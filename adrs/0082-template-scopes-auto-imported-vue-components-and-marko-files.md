# Template Scopes, Auto-Imported Vue Components and Marko Files

## Context and Problem Statement

[ADR 0029](0029-namespace-export-rules-virtual-modules-linked-configs-and-the-node-plugin.md) reads the markup of
`.vue`, `.svelte` and `.astro` files for identifiers and matches them by name, so a template local that shadows an
import (`v-for="item in items"`, `{#each items as item}`, `items.map((item) => …)`) makes an unused import look used.
[ADR 0059](0059-twenty-one-more-plugins-and-commands-run-from-source.md) makes the declaration files
`unplugin-vue-components` and `unplugin-auto-import` generate entries, so every component and composable they list is
used whether or not a template names it; knip compiles each `.vue` file against them and reports a component no
template uses as an unused file.
[ADR 0060](0060-thirty-five-more-plugins-frameworks-task-runners-and-options-written-anywhere.md) and
[ADR 0061](0061-thirty-nine-more-plugins-and-plugins-enabled-by-a-package-json-key.md) say that `qwik` and
`stencil` compile no `.mdx` or Sass files and that `marko` compiles no `.marko` files (GitHub issue #102). skif runs no
compiler ([ADR 0001](0001-mission-and-scope.md)). How far can a static reading close these gaps?

## Decision Drivers

* skif runs no template compiler and no type checker
* The template expressions of Vue, Svelte, Astro and MDX are JavaScript, which oxc parses
* A reading that cannot be completed may make an import look more used, never less
* A component knip reports as an unused file should be one for skif too
* New extraction belongs in `skif-js-syntax`, and library crates do no I/O

## Considered Options

* Parse template expressions with oxc under a scope stack of the block constructs, link registered components per
  template, and read `.marko` files with the existing import and style extractors
* Write a template compiler for each framework
* Document the gaps as limits of a template scan

## Decision Outcome

Chosen option: "Parse template expressions with oxc under a scope stack of the block constructs, link registered
components per template, and read `.marko` files with the existing import and style extractors", because each gap has
a static form that reuses what skif already parses, and a compiler per framework would track four template languages
for the one fact skif needs from them: which names a template uses.

**Template scopes.** Each expression of a template (`{{ }}`, `{ }`, `:prop`, `v-*`, `@event`, Svelte tags and
attributes, Astro and MDX expressions) is parsed by oxc, as TypeScript for Vue and Svelte and as TypeScript with JSX
for Astro and MDX, and oxc's semantic analysis drops the names the expression binds itself: the parameters of
`items.map((item) => <Card item={item} />)`. Vue event handlers that are statements (`count++; save()`) are parsed as
a program. The template locals of the constructs around an expression sit on a scope stack:

* Vue: `v-for` binds its alias for the element's other attributes and its content; `v-slot`, `#name` and
  `slot-scope` bind their props for the content. The stack frame ends with the element's end tag, or at once for a
  self-closing or void element.
* Svelte: `{#each items as item, index (key)}`, `{#await promise then value}`, `{:then value}`, `{:catch error}`,
  `{#snippet name(params)}` and `let:x` (or `let:x={pattern}`) bind their names until `{/…}` or the end tag;
  `{@const x = …}` adds `x` to the enclosing frame, and `{:else}` clears the frame of its block.

Patterns are parsed as the parameters of an arrow function, so destructuring and default values work, and a default
value reads the outer scope. A name bound either way is no use of an import of the same name. An expression or pattern
oxc cannot parse is read token by token, as before, and binds nothing. Tag names are matched as before.

**Auto-imported components.** knip reports a component `components.d.ts` registers but no template uses under
`files`, as an unused file; skif reports it under `unused-files`. A `.d.ts` file whose first 300 characters name
`Generated by unplugin-vue-components` is read by `skif_js_syntax::registered_components`: each property of
`GlobalComponents` and each global `const` (other than Nuxt's `Lazy` ones) whose type is `typeof import('./…')[…]`.
The declaration file's `import()` types of these local components are no edges of the module graph. A `.vue` file
records the tag names of its template (`ModuleInfo::template_tags`), and once the files reached so far are read, each
`.vue` module whose template uses a registered component as `AppButton`, `app-button`, `LazyAppButton` or
`lazy-app-button` imports its default export, as knip's compiler adds `import { default as AppButton }`; a further file
the name is registered from is imported for its side effects. The components these imports reach are read in the next
round and linked in turn. A component registered from a package (`typeof import('vant')['Button']`) stays an import of
the declaration file. The added imports are value imports, so a cycle through them is a `circular-imports` finding as
if it were written.

**Composables.** `auto-imports.d.ts` stays an entry whose composables are all used. knip adds an import of a
composable to each `.vue` and `.ts` file that names it, which would need the names every script reads without binding
them; skif does not record those.

**Marko.** `.marko` files are read the way knip's Marko compiler reads them, with the extractors skif has: the
`import` statements and `import()` calls outside the style blocks (the `.tsrx` extractor), and the imports of the
`<style>` blocks and the concise `style { … }` blocks, whose language is the last part of the name (`style.less`) and
Sass without one. An import of a tag (`import Card from "<card>"`) names no module and is left out. The template and
the component class are not read, so every imported binding counts as used as a whole. A reached `.marko` file uses
the `marko` package. Like `.mdx` and `.tsrx`, `.marko` files are not in the default `project`; the plugin's tag files
are production entries. skif does not read the tag libraries of installed packages (their `marko.json`), so a package
used only through its tags is not credited, and tag names in the markup reach no file.

**Qwik and Stencil.** Nothing changes: skif reads every reached `.mdx` file and Sass stylesheet itself, whatever the
plugins, so the `.mdx` routes of Qwik City and the Sass `styleUrl` of a Stencil component are read without the
compilers knip registers for `@builder.io/qwik-city` and `@stencil/sass`.

**Not done.** Nothing in a template is type-checked: that is the type checker's work, which skif does not run.

### Consequences

* Good, because an import that only a template local of the same name mentions is reported as unused.
* Good, because a registered Vue component no template uses is reported as an unused file, as knip reports it, and
  the components only such a component uses are unused too.
* Good, because the imports of `.marko` files keep their files and packages used.
* Bad, because the scope stack follows only the constructs listed; a local bound another way, such as the name a
  Svelte `{#snippet}` declares, still counts as a use.
* Bad, because tags are matched as written: a component registered under one name and used under another spelling
  than knip tries is not linked.
* Bad, because composables and Marko tag libraries are still credited as before: every listed composable is used, and
  a package used only through its tags is not.

* `crates/skif-js-syntax/src/components.rs`, `crates/skif-js-syntax/src/marko.rs` and `crates/skif-js/src/components.rs`

## Pros and Cons of the Options

### Parse template expressions with oxc under a scope stack of the block constructs, link registered components per template, and read `.marko` files with the existing import and style extractors

* Good, because it reuses the parser, the semantic analysis and the extractors skif has.
* Good, because a template it cannot read degrades to the previous scan.
* Bad, because the block constructs are listed by hand and a new one of a framework needs a change.

### Write a template compiler for each framework

* Good, because the compiler's view of each template would be exact.
* Bad, because it means tracking four template languages and their versions for which names a template uses.

### Document the gaps as limits of a template scan

* Good, because nothing changes.
* Bad, because none of them is a limit of static analysis: each has a static form.
