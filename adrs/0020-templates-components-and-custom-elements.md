# Templates, Components and Custom Elements

## Context and Problem Statement

Framework files use imports from places no module graph sees: the template of a `.vue`, `.svelte` or `.astro` file,
the expressions of an `.mdx` page, the components an auto-import plugin registers by tag, and the custom element
classes a browser instantiates through a tag name. A static reading that matches identifiers by name lets a template
local hide an unused import, and one that never sees a registration reports every element class as unused. skif runs
no compiler ([ADR 0001](0001-mission-scope-and-non-goals.md)). How far does a static reading of templates and
registrations go, and where does a plugin decide what counts?

## Decision Drivers

* A template use counts only when it names the import, not a template local of the same name
* The parser records facts; plugins decide which libraries' conventions apply, per package
* A registered component no template uses is unused, as knip reports it
* Each case reuses the parsers skif already has; no per-framework compiler
* Where the static reading cannot see every use, the wider credit applies

## Considered Options

* Parse template expressions with oxc under a scope stack, link registered components by tag, and record custom
  element registrations in the module facts for plugins to accept
* Keep a token scan of the markup and treat every registered component and element class as used
* Run each framework's compiler

## Decision Outcome

Chosen option: "Parse template expressions with oxc under a scope stack, link registered components by tag, and
record custom element registrations in the module facts for plugins to accept", because each gap has a static form
that reuses what skif parses, and a plugin stays a declarative row.

### Template expressions

* Expressions of Vue and Svelte templates are parsed by oxc as TypeScript, and those of Astro and MDX as TypeScript
  with JSX, under a scope stack of the template's binding constructs (Vue `v-for`, `v-slot`/`#name`/`slot-scope`;
  Svelte `{#each}`, `{#await}`, `{:then}`, `{:catch}`, `{#snippet}`, `{@const}` and `let:`). A name a template binds is
  no use of an import of that name.
* An expression or pattern oxc cannot parse falls back to the token scan and binds nothing.
* A Vue tag uses the names Vue resolves it to: as written, camelized and capitalized. One normaliser in
  `skif-js-syntax` serves template reading and component linking.
* Nothing in a template is type-checked.

### Vue components

* A `.d.ts` file generated by `unplugin-vue-components` registers components; each module whose template tags, static
  `is` values or `resolveComponent('X')` calls name a registered component imports its default export, and the linked
  components are read in turn. Registrations are global to the run. Linked imports are left out of
  `circular-imports`. A component registered from a package stays an import of the declaration file.
* A package where components may be used without a tag skif records keeps the declaration file as an entry that
  credits every registered component: a `.tsx` or `.jsx` project file, a VitePress or VuePress site, a plugin
  `include` wider than `.vue` or not readable statically, a `<template>` in a language other than HTML, or a
  `<script lang="tsx|jsx">`.
* `auto-imports.d.ts` stays an entry: every composable it lists is used.
* Nuxt-generated declaration files are not read this way.

### Other template languages

* Marko: imports and `import()` outside style blocks are read with the `.tsrx` extractor, style block imports are
  read, and a reached `.marko` file uses `marko`. Tag libraries of installed packages (`marko.json`) are not read.
* Qwik `.mdx` routes and Stencil Sass stylesheets are read by skif's own extractors, so no compiler is needed.

### Custom elements

* `skif-js-syntax` records the registrations of the class behind each export (`Export::registrations`):
  * `Define`: the class is passed to `customElements.define(…)`, through a registry resolved by scope;
  * `Decorator { module, name }`: a top-level class carries a decorator imported from `module`;
  * `BaseClassDefine { module, name }`: a class extends an imported base and is registered through its `define`.
* `Define` always counts as a use. Decorator and base-class registrations count only through a plugin enabled for the
  export's package whose `PluginSpec::custom_elements` names the library (`lit`, `catalyst`, `fast`, `stencil`).
* A registered export keeps the types in its signature used, and `explain-usage` reports it as `registered`.

### Taskr

* `taskr` follows taskr's own loading rules: `{T,t}askfile.js` is an entry, `taskr.requires` paths are entries (a
  package name there is a dependency), and every `@taskr/*` and `taskr-*` dependency is used.

### Consequences

* Good, because a template local named like an import hides no unused import or namespace export.
* Good, because a registered Vue component no template uses is reported as an unused file, as knip reports it.
* Good, because web component libraries do not see every element class reported as an unused export, and a further
  library is a plugin row, not parser code.
* Bad, because the scope stack follows only the listed constructs; a local bound another way still counts as a use.
* Bad, because a package with TSX, JSX, a docs site or a wide `include` still credits every registered component.
* Bad, because component registrations are global, so a tag in one workspace links a component another registers.
* Bad, because a class registered in a form the parser does not record (a registry passed as a parameter, a class
  expression) is still reported.

## Pros and Cons of the Options

### Parse template expressions with oxc under a scope stack, link registered components by tag, and record custom element registrations in the module facts for plugins to accept

* Good, because each fact comes from a parser skif already runs, and plugins only name libraries.
* Bad, because each binding construct of each template language is modelled by hand.

### Keep a token scan of the markup and treat every registered component and element class as used

* Good, because it is simple and never reports a used component.
* Bad, because shadowed imports look used and unused components and elements are never reported.

### Run each framework's compiler

* Good, because templates would be read exactly as the framework reads them.
* Bad, because it needs a JavaScript runtime and four compilers for the one fact skif needs: which names a template
  uses.
