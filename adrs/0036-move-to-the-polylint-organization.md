# Move to the polylint Organization: Repository, Tap, Bucket and Release Credentials

## Context and Problem Statement

skif was developed as `Goldziher/skif`, a personal repository, and [ADR 0027](0027-distribution-and-release.md)
publishes it to the personal Homebrew tap `Goldziher/homebrew-tap` and Scoop bucket `Goldziher/scoop-bucket`. The
release workflow pushes to both with `HOMEBREW_TOKEN`, a personal access token stored in this repository. The same
token moves the floating tag, because `GITHUB_TOKEN` cannot push a tag onto a commit that changes a workflow. The
formula and the manifest are generated by `scripts/homebrew-update.sh` and `scripts/scoop-update.sh` from
`checksums.txt`, and the tap has no bottles.

The repository has moved to the `polylint` GitHub organization, next to the other polylint tools. The organization
runs one Homebrew tap and one Scoop bucket for all of them, and pushes to them with an organization GitHub App. Where
does skif publish from now, with which credentials, and what happens to the releases built before the move?

## Decision Drivers

* One owner for the repository, the documentation site, the tap, the bucket and the npm scope
* No personal access token in the release path
* Every polylint tool publishes to the tap and the bucket in the same way
* Releases published before the move still install and still verify
* The Linux install keeps working on every glibc, as ADR 0027 requires

## Considered Options

* Keep the personal tap and bucket and the personal token
* The organization tap and bucket, written by the organization GitHub App with the shared xberg-io actions
* The organization tap and bucket, written by this repository's own scripts with the App token

## Decision Outcome

Chosen option: "The organization tap and bucket, written by the organization GitHub App with the shared xberg-io
actions", because it removes the personal token and makes skif's formula and manifest work like those of the other
polylint tools.

* The repository is `polylint/skif`. The documentation is served at `https://polylint.github.io/skif/`, the Action is
  `polylint/skif@v0.M`, and the schema URL written into generated configurations is
  `https://raw.githubusercontent.com/polylint/skif/main/schema/skif.schema.json`. GitHub redirects the old repository
  URLs, but the old Pages URL does not redirect, so every link names the organization.
* Homebrew: `brew install polylint/tap/skif` from `polylint/homebrew-tap`. Scoop:
  `scoop bucket add polylint https://github.com/polylint/scoop-bucket`. Both are pushed by
  `polylint-release-helper[bot]`, using a token from `actions/create-github-app-token` (`BOT_APP_ID` and
  `BOT_APP_PRIVATE_KEY`, organization secrets) that is scoped to the one repository it writes.
* The formula and the manifest are templates in `scripts/publish/`, rendered by
  `xberg-io/actions/publish-homebrew-source-formulas` and `publish-scoop-manifests`, which hash the release archives
  themselves. `scripts/homebrew-update.sh` and `scripts/scoop-update.sh` are removed. The formula keeps the platforms
  of ADR 0027: macOS on arm64 and Intel, and on Linux the glibc archive from `SKIF_GLIBC_FLOOR` up, the static musl
  archive below it.
* Bottles are built for macOS arm64 (on `macos-26`), Linux x86_64 and Linux arm64 by
  `xberg-io/actions/homebrew-build-bottles`. They are uploaded to the release and merged into the formula by
  `homebrew-merge-bottles` only when all three are built. The Linux bottles carry the glibc archive, so the formula's
  `pour_bottle?` check skips them below the glibc floor and the musl archive is installed instead. Intel macOS has no
  bottle and installs the archive.
* The floating tag is moved with an App token that has `contents` and `workflows` write on this repository.
  `HOMEBREW_TOKEN` is retired.
* Build attestations name the repository whose workflow signed them. The Action and the pre-commit launcher check a
  release against `polylint/skif`; a release up to v0.6.0, built before the move, is also accepted when
  `Goldziher/skif` attested it (`scripts/lib/attestation.sh`). Later releases, and mirrors set through the
  `repository` input or `SKIF_REPOSITORY`, have no fallback.

This amends the Homebrew and Scoop channel, the source of the formula's glibc floor and the Action pin in the
documentation as ADR 0027 states them. The rest of ADR 0027 holds, including the release order: the tap and the
bucket are written after the public release and `cargo binstall` are verified, and a prerelease updates neither.

### Consequences

* Good, because no personal token takes part in a release, and each App token can write only the one repository it
  needs.
* Good, because the tap gets bottles, so a supported platform pours a bottle and only Intel macOS downloads the
  archive.
* Good, because skif's formula and manifest follow the same templates and actions as the other polylint tools.
* Bad, because the release depends on the xberg-io actions and on the organization App being installed on the tap,
  the bucket and this repository with the right permissions.
* Bad, because users of `goldziher/tap/skif` and the `goldziher` Scoop bucket must switch to the organization's.
* Neutral, because crates.io and npm trusted publishing follow the repository through the move, and the npm packages
  were already under `@polylint` ([ADR 0035](0035-publish-the-npm-packages-under-the-polylint-scope.md)).

### Confirmation

* `scripts/test-release-scripts.sh` renders both templates the way the release does and checks every archive hash,
  the URLs, the glibc floor against `SKIF_GLIBC_FLOOR`, the bottle guard, and that the result is valid Ruby and JSON.
* `scripts/test-install-scripts.sh` checks that a v0.6.0 release verifies against `Goldziher/skif` when
  `polylint/skif` has no attestation for it, and that a later release and a mirror do not fall back.
* `rg -i goldziher` in the repository finds only the maintainer's personal references, the repositories that stay
  under that account, historical records and the pre-move attestation identity.

## Pros and Cons of the Options

### Keep the personal tap and bucket and the personal token

* Good, because nothing changes for current users.
* Bad, because an organization repository would publish through one person's account and token.

### The organization tap and bucket, written by the organization GitHub App with the shared xberg-io actions

* Good, because it needs no stored token and matches the other polylint tools.
* Good, because the actions bring bottles and a retry on a concurrent push to the shared tap.
* Bad, because it depends on actions maintained outside this repository.

### The organization tap and bucket, written by this repository's own scripts with the App token

* Good, because the release would depend on nothing outside this repository.
* Bad, because skif would keep its own formula generator and no bottles, unlike the other tools in the same tap.
