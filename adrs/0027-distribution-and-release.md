# Distribution and Release: One Name, One Version, One Release Workflow

## Context and Problem Statement

skif's users are JavaScript developers, Rust developers who embed the library, and CI pipelines. Each group installs
tools differently: as a dev dependency from npm, with `cargo install` or `cargo binstall`, with Homebrew or Scoop,
as a GitHub Action, or from a release archive. A release that reaches some of these channels and not others, or that
names a different version on each, breaks installs and makes a bug report impossible to place.

Which channels does skif ship through, how is the npm package built, how are versions and floating tags kept, and in
what order does a release publish?

## Decision Drivers

* The same command name, `skif`, on every channel, and one version everywhere
* JavaScript users install skif like any dev dependency: offline at first run, no install scripts
* The GitHub release is never visible with missing archives, and a failed release is finished by re-running it
* Users pinned to a release line get patches without breaking changes
* The default install works on every Linux, whatever its glibc
* A registry that refuses or has not yet created a name does not block the rest of a release

## Considered Options

* One name on every channel, a napi-rs addon on npm, synchronized versions and one idempotent release workflow
* A Node launcher that spawns a binary from per-platform npm packages
* A download-on-install npm package
* Separate release workflows per channel

## Decision Outcome

Chosen option: "One name on every channel, a napi-rs addon on npm, synchronized versions and one idempotent release
workflow", because it keeps installs offline and script-free, generates the platform packages instead of maintaining
them, and gives every channel the same version from one build.

### Channels

* The project, the command, the crates and the configuration are named `skif`. There is no PyPI package: a Python
  wrapper would serve no user who does not already have Node.
* crates.io: every published crate ([ADR 0002](0002-crates-publishing-and-repository-consistency-checks.md)), with
  the binary in `skif-cli` (`cargo install skif-cli`).
* cargo-binstall: metadata on `skif-cli` that points at the release archives. The Linux gnu triples are redirected to
  the static musl archives, because binstall cannot see the host's glibc and has no fallback; the glibc archives stay
  on the release page.
* GitHub release archives for `aarch64-apple-darwin`, `x86_64-apple-darwin`, the gnu and musl Linux triples of x64
  and arm64, and `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, each with `LICENSE` and the attributions,
  plus `checksums.txt`.
* npm: the umbrella `skif-cli` with its platform packages.
* The composite GitHub Action at the repository root.
* Homebrew (`Goldziher/homebrew-tap`) and Scoop (`Goldziher/scoop-bucket`), with manifests generated by scripts from
  `checksums.txt`.
* Git hooks ([ADR 0028](0028-editors-agents-and-git-hooks.md)).
* `SKIF_GLIBC_FLOOR` in `scripts/lib/libc.sh` is the one definition of the glibc the gnu builds need; the Homebrew
  formula takes it from there, and the build matrix is checked against it.

### The npm package

* The umbrella is a napi-rs package: a Node-API addon built from the Rust library and loaded in-process, exposing the
  `skif` bin and a programmatic API. It is ESM only, has no install scripts and works offline. `engines` is
  `node >=22` and `bun >=1` ([ADR 0030](0030-supported-versions-and-the-end-to-end-matrix.md)).
* npm refuses the name `skif` as too close to existing packages, so the umbrella is `skif-cli`, the same name as the
  crate. Its bin stays `skif`, and Bun's form is `bunx -p skif-cli skif`. `napi.packageName` stays `skif`, so the
  platform packages are `skif-<platform>`.
* napi-rs generates the platform packages for the macOS and Linux (gnu and musl) targets, with their `os`, `cpu` and
  `libc` fields, and writes them into the umbrella's `optionalDependencies`, so the list cannot drift from the build
  matrix.
* Windows has no npm package until both `skif-win32-x64-msvc` and `skif-win32-arm64-msvc` exist on npm with the
  repository's trusted publisher configured, because npm trusted publishing can only be set up on an existing
  package. Until then there is no Windows addon build, load, install or verification job, `npx skif-cli` on Windows
  fails at import, and the documentation sends Windows users to the release archives, `cargo binstall` and Scoop. The
  release that restores them re-adds the two targets to `napi.targets`, with the MSVC runtime linked statically and
  the arm64 addon cross-built and tested on an arm64 runner, and its own record.
* `check-npm-packages-exist.sh` stops a release whose npm packages do not all exist on the registry.

### Build profiles

* The CLI binaries use `[profile.release]` with `panic = "abort"`.
* The addon uses `[profile.node]`, which inherits the release profile with `panic = "unwind"` (`napi build --profile
  node`), so a panic becomes a JavaScript exception instead of ending the host process.

### Versions and tags

* One version on every surface: the workspace version of every crate, the internal `=` pins, the npm umbrella and
  every platform package, `poly-hooks.toml`, the pre-commit launcher and the agent plugin manifests.
  `scripts/release-bump.sh` rewrites them together and `scripts/check-versions.sh` fails when any two disagree.
* Floating tags: from 1.0, a release moves `vN`. A 0.x minor may break, so a 0.x release moves `v0.M` and `v0` never
  moves. The Action resolves `vN` and `vX.Y` to the newest matching release. Documentation pins the Action as
  `Goldziher/skif@v0.M` of the latest minor, rewritten by the bump and checked by `scripts/check-doc-pins.sh`.
* A release ships when it is complete. A name-reservation upload to crates.io or npm is not a release: it is not
  announced, installed by any channel or tagged. Documentation never promises work for a later release.

### The release workflow

`publish.yaml` is one hand-written workflow and is never renamed, because crates.io and npm trusted publishing (OIDC)
are bound to its file name. A tag is released only when it is on `main`, `CHANGELOG.md` has its section and its
commit has a green CI run (`scripts/check-release-gate.sh`). The order:

1. create a draft GitHub release;
2. build every archive and addon target, and smoke-test them;
3. upload the archives and `checksums.txt`;
4. publish the crates leaves-first, so a crate never depends on an unpublished sibling;
5. publish the npm platform packages, then the umbrella, so the umbrella never lists a missing package;
6. verify the published npm package under every supported Node line and the newest Bun;
7. promote the draft once every expected asset is present, then verify `cargo binstall` against it;
8. move the floating tag, and publish the Homebrew and Scoop manifests.

Every step probes for what already exists and skips it, so a re-run completes a failed release. The registries are
not atomic: a run that fails after publishing some crates leaves a partial version there until it is re-run. A
dry-run input builds everything and skips every irreversible step.

### Consequences

* Good, because the command is `skif` everywhere, and JavaScript users pin it in their lockfile with no network
  access at first run.
* Good, because Node and Bun callers can use skif in-process without spawning a binary.
* Good, because the GitHub release is never visible with missing archives, and the install channels people follow
  move only after verification.
* Good, because users pinned to `@v0.M` take patches only, and `cargo binstall` works on every Linux.
* Bad, because the npm package name and the command differ, so `npx skif` is not this tool.
* Bad, because Windows users cannot install from npm until the names exist, and the npm and archive target sets
  differ.
* Bad, because a bad crate version cannot be unpublished, only yanked, and a single failing target blocks the
  release by design.
* Bad, because the version appears in many files; the bump script and the consistency check are what keep them
  equal.

### Confirmation

* `scripts/check-versions.sh` (the `consistency` job) and `scripts/test-release-scripts.sh`, which bumps a copy of
  the tree and requires every surface to follow.
* `scripts/check-npm-tarballs.sh` requires exactly the umbrella and the platform packages `napi.targets` generates,
  with matching `optionalDependencies`; `scripts/test-npm-published.sh` covers `check-npm-packages-exist.sh`.
* `scripts/release-assets.sh` lists the assets the promote step requires, and `scripts/check-archive.sh` checks each
  archive holds the binary and its notices.
* `scripts/release-floating-tag.sh` computes `vN` or `v0.M`; `scripts/check-doc-pins.sh` checks the documented pins.
* `scripts/check-glibc-floor.sh` checks the gnu binaries against `SKIF_GLIBC_FLOOR`, and
  `scripts/check-libc-selection.sh` checks the installers pick the right libc flavour.
* `scripts/check-release-gate.sh` refuses an unready tag.
* The `verify_npm` and `verify_binstall` jobs of `.github/workflows/publish.yaml` run the published packages on clean
  runners and fail the release when they do not print the released version.

## Pros and Cons of the Options

### One name on every channel, a napi-rs addon on npm, synchronized versions and one idempotent release workflow

* Good, because platform manifests and the optional dependency list are generated from the build matrix.
* Good, because one workflow orders every channel and finishes on a re-run.
* Bad, because the addon needs its own build profile and per-target build jobs, and a Node-API floor excludes old
  Node versions.

### A Node launcher that spawns a binary from per-platform npm packages

* Good, because the npm package is the same binary as every other channel.
* Bad, because the platform packages and the launcher are hand-maintained, and library callers pay a process start.

### A download-on-install npm package

* Good, because the npm package is small.
* Bad, because it runs an install script and needs the network at install, which locked-down CI forbids.

### Separate release workflows per channel

* Good, because a failing channel does not hold up the others.
* Bad, because channels drift apart in version and timing, and OIDC bindings multiply.
