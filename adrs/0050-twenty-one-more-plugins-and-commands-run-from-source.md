# Twenty-One More Plugins: Widely Used Tools, Commands Run From Source and Imported Call Options

## Context and Problem Statement

The plugin table holds 105 plugins ([ADR 0036](0036-thirty-nine-more-knip-plugins-by-real-world-usage.md), [ADR 0049](0049-js-corrections-from-adjudicating-knip-disagreements.md)). Issue #39 lists the knip plugins of widely used tools that are still missing (`vue`, `mdx`, `next-mdx`, `parcel`, `electron-forge`, the unplugin family, `serverless-framework` and others), three that read commands from source files instead of configs (`execa`, `zx`, `nano-spawn`), and deeper reading for shared plugins: Starlight component overrides, Azure Pipelines script steps and Sapper.

Several of these cannot be a table row and a config resolver alone. `next-mdx` and `starlight` find their options in a call inside the config (`createMDX({ options })`, `starlight({ components })`), which the static extraction of the exported value does not see; `pino`, `execa`, `zx` and `nano-spawn` read calls in ordinary source files; `lit` and the unplugin compilers change how source files are compiled or which exports count as used.

Which plugins are added, how are calls in source read without running code, and where does skif deliberately not follow knip?

## Decision Drivers

* A plugin follows knip 6.44.1's enablers, config files, entry and production patterns and config-to-dependency resolution ([ADR 0036](0036-thirty-nine-more-knip-plugins-by-real-world-usage.md))
* Configs and sources are read statically and never executed ([ADR 0010](0010-js-analysis-on-oxc.md))
* A mechanism shared by several plugins is better than a parser per plugin
* Every plugin has a fixture test, and the plugin lists in the documentation are checked against the code

## Considered Options

* Add the plugins that fit the plugin model, with one shared extraction of calls of imported functions, and leave out those that need a compiler or export hook
* Add only the plugins that are a table row and a config resolver
* Add a visitor hook to the module graph that plugins register, as knip does

## Decision Outcome

Chosen option: "Add the plugins that fit the plugin model, with one shared extraction of calls of imported functions", because it covers the listed tools except two with one small addition to `skif-js-syntax`.

The added plugins are `vue`, `mdx`, `next-mdx`, `pre-commit`, `parcel`, `electron-forge`, `unplugin-auto-import`, `unplugin-vue-components`, `unplugin-vue-router`, `github-action`, `pino`, `next-intl`, `dependency-cruiser`, `commitizen`, `serverless-framework`, `starlight`, `execa`, `zx`, `nano-spawn`, `azure-pipelines` and `sapper`. The table holds 126 plugins.

`skif-js-syntax` gains `extract_imported_calls`: every call and tagged template in a file whose function is imported from given modules (`import`, `import * as`, or a top-level `require`), with its arguments evaluated by the static evaluator of [ADR 0010](0010-js-analysis-on-oxc.md) and a tagged template's raw text with its substitutions replaced by a placeholder. `next-mdx` and `starlight` apply it to the config source; `pino`, `execa`, `zx` and `nano-spawn` apply it, from `resolve_workspace`, to the source files that mention the library, as `aws-cdk` reads `new NodejsFunction(…)`. A command found this way is a script, parsed by the script parser like a `package.json` script.

A plugin's `package_json_key` may name a nested key with `.` (`config.commitizen`, `config.forge`).

Not added:

* `unplugin-icons` is added by another change.
* `glob` has no enabler in knip, only argument rules for its binary; the script parser reads `glob -c "<command>" <patterns>` instead, and no table row is added.
* `lit` marks classes registered as custom elements as used exports. Plugins report entries, dependencies and scripts, not export usage, so it needs a hook in the export rules first.

Where skif differs from knip:

* `unplugin-auto-import` and `unplugin-vue-components` make the declaration files they generate entries (a `.d.ts` at the top level or under `src` whose header names the generator). knip compiles each `.vue` and `.ts` file against those maps, which also tells which generated globals a file uses; skif counts every component or composable the generated file lists as used.
* `unplugin-vue-router` is enabled by `vue-router` too, as knip is, and contributes routes only when `unplugin-vue-router` is a dependency or a declaration file generated by `vue-router` exists.
* `vue` reads an object `configureWebpack` as a webpack config and does not call a function one. `vue-cli-service lint` (`lint` as the first positional argument) credits `@vue/cli-plugin-eslint` whether or not `vue.config.*` exists.
* `electron-forge` also reads the options of `new VitePlugin({ … })` and `new WebpackPlugin({ … })` in `forge.config.*`, which knip sees on the loaded instance.
* `serverless-framework` resolves `${file(…)}` variables, with an optional key path, and no other variable kind; a `handler` holding a variable or a pattern (`$`, `` ` ``, `*`, `{`, `}`) is skipped.
* `github-action` leaves out `dist/` and `build/` files as build output; knip also removes them from the project files.
* `zx` also reads `$` imported from `zx`, in files that import `zx/globals` and in files whose shebang runs `zx` through another command (`#!/usr/bin/env -S npx zx`), where knip reads only files that start with `#!/usr/bin/env zx`.
* `execa` and `nano-spawn` leave computed arguments out, as knip does, but skip the whole call when a literal argument is not a plain word, where knip drops that word and keeps a command of different meaning. `execa` also reads the default export of execa 5 and earlier (`execa(…)`, `execa.sync`, `execa.command`, `execa.node`). `nano-spawn` requires the function to be imported from `nano-spawn`, where knip takes any function named `spawn`.
* `azure-pipelines` and `sapper` have no knip counterpart, as `tap` had none ([ADR 0049](0049-js-corrections-from-adjudicating-knip-disagreements.md)). `azure-pipelines` treats the `script` and `bash` steps of `azure-pipelines.yml`, `.azure-pipelines/**` and the templates they include as scripts, honouring `workingDirectory` as `github-actions` honours `working-directory`; `sapper` declares Sapper's fixed layout.

Playwright reporters named in the config were already dependencies, so that item of the issue needed no change.

### Consequences

* Good, because the false findings of 21 more tools disappear without running any tool.
* Good, because one extraction serves config options passed to calls and commands run from source, and later plugins of the same shape need no new parser.
* Neutral, because the source-reading plugins read the package's source files a second time when the library is a dependency; files that do not mention the library are not parsed.
* Bad, because a command or option computed at run time is not seen; such a file shows as an unlisted binary or an unused file until the form gets support.
* Bad, because `lit` stays uncovered until export rules accept plugin input.

### Confirmation

* `crates/skif-js-plugins/tests/plugins.rs` lists the 126 ids in `ADR_IDS` and has a fixture test for each new plugin; `scripts/tests.rs` covers `glob -c`.
* `crates/skif-js-syntax/tests/imported_calls.rs` covers named, default, member and required imports, globals and tagged templates.
* `scripts/check-plugin-list.sh` fails when the plugin lists or counts in the README files and the website differ from the code.
* `adrlint lint adrs`, `adrlint format --check adrs` and `adrlint lock --check` pass.

## Pros and Cons of the Options

### Add the plugins that fit the plugin model, with one shared extraction of calls of imported functions

* Good, because it covers all but two of the listed tools.
* Bad, because the source-reading plugins scan files outside the module graph.

### Add only the plugins that are a table row and a config resolver

* Good, because it needs no change outside the plugin crate.
* Bad, because `next-mdx`, `starlight`, `pino`, `execa`, `zx` and `nano-spawn` would be rows that find nothing.

### Add a visitor hook to the module graph that plugins register

* Good, because each source file would be parsed once for every plugin, and `lit` could mark exports.
* Bad, because it couples the plugin crate to the graph's traversal, a larger change than the plugins it serves.
