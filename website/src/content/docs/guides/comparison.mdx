skif builds on three projects and covers their three jobs in one tool. They remain excellent, focused tools.

| Tool | Scope | Relation to skif |
| --- | --- | --- |
| [sherif](https://github.com/QuiiBz/sherif) | Zero-config monorepo manifest rules | skif began as a fork; the manifest rules are ported with stable ids and `skif.toml` configuration, and the sherif behaviours fixed in the port are [listed in the migration guide](../migrating/#fixed-relative-to-sherif). |
| [syncpack](https://github.com/JamieMason/syncpack) | Version consistency, semver ranges, catalogs | Same problem space; skif's policy rules reuse syncpack's specifier model, vendored in `skif-specifier`. |
| [knip](https://github.com/webpro-nl/knip) | Unused files, exports and dependencies | Same problem space; skif's analysis runs on oxc, with static config extraction instead of running tools. |
| [manypkg](https://github.com/Thinkmill/manypkg) | Workspace consistency checks and fixes | Overlapping manifest checks; skif adds a rule registry, severities and a library API. |

skif offers all three kinds of checks in one tool with one configuration file and one report format.

## Capabilities

The tables compare skif with sherif 1.13.0, syncpack 15.3.3 and knip 6.45.1. Every cell of the other tools was
checked against their source code at those release tags, and where it depends on behaviour, by running the released
version on a test workspace ([sources](#sources)). A cell is Yes, No, or Partial, which the numbered note below the
table explains. The skif column describes the `main` branch and names the rule or command that does the work; every
rule is on the [rules pages](../../rules/). How often skif and knip report the same findings on real repositories is
under [Parity with knip](#parity-with-knip).

| Another package manager's commands in Dockerfiles, workflows and shell scripts | Yes: `foreign-package-manager-command` | No | No | No |
| Lockfile checks: stray lockfiles, bans and families over the lockfile, stale patches | Partial (12) | No | No | No |
| `package.json` formatting: key order, `exports` conditions, shorthands | Yes: `skif format`, `package-json-format` | Partial (13) | Yes: `syncpack format` | No |
| Newer published versions from the registry | Yes: `skif update`; `skif update --check` only reports | No | Yes: `syncpack update`; `syncpack update --check` only reports | No |
| Dependency inventory by group | Yes: `skif list`, `skif json` | No | Yes: `syncpack list`, `syncpack json` | No |

1. Sorting dependency maps only: `syncpack format` sorts the keys listed in `sortAz`, by default `dependencies`,
   `devDependencies`, `peerDependencies` and `resolutions`. syncpack has none of the other checks.
2. `dependencies` and `devDependencies` only, and only specifiers that parse as semver; `catalog:`, `workspace:` and
   `file:` specifiers are skipped.
3. `unsync-similar-dependencies` checks a fixed list of ten families (tRPC, React, Next.js, Storybook, Turborepo,
   Prisma, typescript-eslint, ESLint Stylistic, Playwright, Lexical) within each `package.json`, not across packages.
   The list cannot be changed and the rule has no fix.
4. A `policy: "catalog"` version group (`NotUsingCatalog`, `MissingFromCatalog`) over pnpm catalogs
   (`pnpm-workspace.yaml`) and Bun catalogs (the root `package.json`); Yarn catalogs in `.yarnrc.yml` are not read.
   Outside such a group, a catalog entry that differs from the other instances is a version mismatch.
5. `unused-catalog-entries` and `unresolved-catalog-references`. `unused-catalog-entries` reports nothing unless
   `[catalog] report-unused-entries = true` is set.
6. Unresolved `catalog:` references only, inside a `policy: "catalog"` version group, as a warning (an error with
   `strict: true`); unused entries are not reported.
7. A version group with `dependencies: ["$LOCAL"]`, `dependencyTypes: ["!local"]` and `pinVersion: "workspace:*"` pins
   the specifier; there is no check of its own.
8. An `isBanned` version group with `specifierTypes: ["file", "link"]`; `portal:` specifiers are not recognised.
9. A `policy: "sameRange"` version group over `peer` and `dev` reports ranges that do not overlap; it compares the
   declared ranges, not an installed version.
10. `root-package-manager-field` only: the root `packageManager` or `devEngines.packageManager` field must be present;
    its value is not checked.
11. `customTypes` bring `package.json` fields such as `packageManager` and `engines.node` into version groups; no other
    file is read.
12. `stray-lockfile` reads no lockfile and works for every package manager. The lockfile scope of `banned-dependency`
    and of dependency families reads only `pnpm-lock.yaml` format 9 (pnpm 9 to 12); `stale-patched-dependencies`
    reads `pnpm-lock.yaml` and `bun.lock`. `yarn.lock`, `package-lock.json` and `bun.lockb` are not read (see
    [Lockfile](../workspaces/#lockfile)).
13. `unordered-dependencies` sorts dependency maps; no other formatting.

1. Added in knip 6.45.0: unused `imports` entries by default, and unused `exports` subpaths with
   `includeSubpathExports`. skif reports the `imports` entries with `unused-subpath-imports` and the `exports`
   subpaths with `unused-subpath-exports`, which is off by default. In production mode skif reports neither, since
   test files may be the only importers; knip reports both.
2. `.vue`, `.svelte` and `.astro` (scripts and templates), `.mdx`, `.marko` and `.tsrx`, and the imports of
   stylesheets (`.css`, `.scss`, `.sass`, `.less`, `.pcss`, `.styl`, `.stylus`), read without a compiler (see
   [`[js]`](../../reference/configuration/#js)).
3. Built-in import extraction for `.astro`, `.vue`, `.svelte`, `.mdx`, `.marko`, `.tsrx`, `.css` (Tailwind), `.less`,
   `.sass`, `.scss`, `.styl`, `.stylus`, `.prisma` and `.md` (unplugin-vue-markdown); a custom compiler can replace any
   of them.
4. Tool configurations are read statically ([ADR 0001](https://github.com/Goldziher/skif/blob/main/adrs/0001-mission-scope-and-non-goals.md));
   a package whose configuration skif cannot read is listed under `incomplete-packages` in the JSON report. After
   writing, `--fix` and `skif update` run the package manager's install, which runs the project's install scripts;
   `--no-install` skips it.
5. sherif reads only `package.json` and `pnpm-workspace.yaml`. When `--fix` changes a file it runs `npm install`,
   `yarn install`, `pnpm install` or `bun install`; `--no-install` skips it.
6. syncpack reads no tool configuration and never runs the package manager, but its own configuration file, when it
   is JavaScript or TypeScript (`.syncpackrc.{js,ts,mjs,cjs}`, `syncpack.config.{js,ts,mjs,cjs}`), is imported by a
   `node` process.
7. knip's plugins load configuration files such as `vite.config.ts` with jiti, and knip exits `2` when one fails to
   load.

| Configuration format | TOML: `skif.toml`, `.skif.toml` | `sherif` key in the root `package.json`, CLI flags | `.syncpackrc`, `.syncpackrc.{json,yaml,yml,js,ts,mjs,cjs}`, `syncpack.config.{js,ts,mjs,cjs}`, `package.json#syncpack` or `#config.syncpack` | `knip.json`, `knip.jsonc`, `.knip.json`, `.knip.jsonc`, `knip.ts`, `knip.js`, `knip.config.ts`, `knip.config.js`, `package.json#knip` |

1. `--allow-remove-files` is needed to delete files; there are no other levels.
2. `fix` selects dependencies (`--dependencies`, `--dependency-types`, `--specifier-types`), not issue types.
3. `--dry-run` of `fix`, `format` and `update` lists the changes without writing them; it prints no diff.
4. knip's guide to gradual adoption builds an "actionable baseline" by fixing configuration gaps and caps CI with
   `--max-issues`; no file records accepted findings.
5. Version, semver and update groups with `isIgnored` take an optional `label`, free text shown as the group's
   heading.
6. `skif.toml` files merge from the root up to the git root, `extends` names more, and `[[overrides]]` select packages
   and files ([Sharing configuration](../sharing-configuration/)).
7. One file, with no `extends`; its `workspaces` map sets entry, project, ignore and plugin options per workspace
   directory or glob, while `rules`, `include`, `exclude`, `compilers`, `tags` and `cycles` are set for the whole run.

## Parity with knip

skif's JS analysis covers the issue types of knip 6.45:

- **Coverage.** Every issue type of knip 6.45 has a skif rule, 19 in all (the list is in the
  [migration guide](../migrating/#which-tool-runs-which-rule)), and `skif migrate` translates a knip configuration.
  skif reads tool configurations statically and never runs project code.
- **Speed.** Full skif runs are timed against knip on pinned public repositories; see [Performance](#performance).
- **Precision.** Precision and recall on a generated workspace with seeded dead code are on the
  [benchmarks page](../benchmarks/#precision-on-seeded-dead-code).
- **Agreement.** Real repositories have no answer key, so a weekly job runs both tools on pinned public repositories
  and compares the findings per issue type. The [agreement table](../benchmarks/#agreement-with-knip), generated from
  the committed baseline of that comparison, gives the share of each tool's findings the other reports too, and what
  is counted apart.

A package whose entry files skif cannot all know (a tool configuration it cannot read) is listed under
`incomplete-packages` in the JSON report. skif does not judge its unused dependencies; where the configuration's scope
is narrowed it judges the files, exports, types and members outside that scope, and otherwise none of them (see
"Incomplete entries" under [`[js]`](../../reference/configuration/#js)). knip still reports there.

A dependency on a workspace member that nothing can import or run is not reported unused: a member whose
`package.json` has no `main`, `module`, `exports`, `bin`, `browser`, `types` or `typings` and that holds no source
file, such as a tooling, asset or style package. Such a dependency orders tasks (Turborepo's `^build`, Nx's task
dependencies), and knip reports it. A member with one of those fields or a source file is judged as before; when it
is listed only to order tasks, add it to `ignore-dependencies` with a `reason`.

A package with a reached `.svelte` file uses `svelte`, the compiler of its components; knip credits `svelte` only
where a file or a configuration names it. skif reads the exports of a component's module script
(`<script context="module">`, `<script module>`) and reports the unused ones; the exports of the instance `<script>`
(`export let`) are props, not exports. knip reads only the imports of a `.svelte` file, so it reports none of its
exports.

The remaining differences each have an open issue, and their size is in the
[agreement table](../benchmarks/#agreement-with-knip):
`unlisted-dependencies` ([#96](https://github.com/Goldziher/skif/issues/96)), `unlisted-binaries`
([#97](https://github.com/Goldziher/skif/issues/97)), `unused-dependencies`
([#98](https://github.com/Goldziher/skif/issues/98)), `unresolved-imports`
([#99](https://github.com/Goldziher/skif/issues/99)) and `unused-files`
([#100](https://github.com/Goldziher/skif/issues/100)).

Two differences are knip's and stay counted, as the comparison cannot tell them apart from its data: knip reports the
members of an enum used as a whole value (passed or returned, `@IsEnum(E)`, `Object.values(E)`, `keyof typeof E`,
`` `${E}` ``), also in the file that declares it, which makes every member reachable, and knip has no esbuild plugin, so it reports the `entryPoints` of an esbuild
script, and the files they reach, as unused.

knip does not read the specifiers of test-runner mocks. skif does: a `vi.mock`, `jest.mock` or `jest.requireActual`
keeps the file it names in use, and a relative or aliased mock of a file that does not exist is reported by
`stale-mocks`, an error that knip has no counterpart for (`skif migrate --profile exact` turns it off). Such a mock
is not an `unresolved-imports` finding, so unresolved imports compare with knip's `unresolved`.

skif never reports a declaration file (`.d.ts`, `.d.mts`, `.d.cts`) as an unused file: TypeScript loads ambient
declarations without an import, and a published package's typings are read by its consumers, so every declaration
file is an entry. knip reports one that nothing imports.

A namespace passed as an argument is a use of the whole module in both tools, with one exception in skif: a
test-runner spy with a literal member name (`vi.spyOn(ns, "a")`, `jest.spyOn(ns, "a")`, Jasmine's `spyOn(ns, "a")`)
reads member `a` only, as `ns.a` does
([ADR 0018](https://github.com/Goldziher/skif/blob/main/adrs/0018-export-namespace-and-member-rules.md)).
knip counts such a spy as a use of every export, so skif reports the exports that nothing else reads and knip does
not.

A use of a module object as a whole (a namespace passed around, spread, indexed with a computed key or named in
`typeof ns`, and `require("./m")` or `import("./m")`) reaches the values of the module only. In skif it uses every value
export and none of the module's interfaces and type aliases: those stay used when they are read by name (`ns.Type`) or
when the importer exports the namespace itself (`export default ns`, `export = ns`), and are reported by
`unused-types` otherwise. A file loaded with `new URL("./x", import.meta.url)` is no module object but a program of its
own, so it keeps every export used, as an entry does
([ADR 0018](https://github.com/Goldziher/skif/blob/main/adrs/0018-export-namespace-and-member-rules.md)).
knip reports such types only under `nsTypes`, which is off by default, and not at all for a spread or an `import()`.

knip merges the tsconfig `paths` of every workspace, so an import that only another package's `paths` map resolves
for it. skif resolves an import with the configuration the importing file follows, as TypeScript does: such an import
is reported by `unlisted-dependencies` with the detail `ForeignTsconfigPaths`, a message that names the config whose
`paths` map it, and no advice to add a dependency. The fix is to add the mapping to the importing package's tsconfig,
or to import the module by the name of the package that exports it. A pattern with no literal prefix (`*`) is not
counted, as it maps every specifier, and neither is a pattern whose targets are no source file of the workspace (one
into `node_modules`, or to missing files). An import of a workspace package, of a package a manifest lists or of an
installed package keeps the advice to add it to `package.json`.

Both tools report a package that a tool config names and no manifest lists (a `tsconfig` `extends`, an Oxlint or
ESLint plugin, a Prisma generator) at the config. knip reads some of them as files to resolve, so one with an unscoped
name that it cannot find is reported as unresolved or not at all; skif reports each as unlisted, with the detail
`ConfigReference`. A Sass importer
that a config builds in code (`sassOptions.importer` from `sass-alias`) is not read, so the imports its aliases serve
(`@import "@sass/abstracts/mixins"`) are reported as unlisted packages; list the alias in `ignore-dependencies`
(`"@sass/*"`).

A `package.json` script or a workflow step that runs a command after `cd <dir>` (`cd sub && pnpm exec rspack`) is
judged by knip at the script's own package, so a binary the workspace package in `sub` provides is reported unlisted
there and its provider unused in `sub`. skif credits the command to the workspace package the directory is in.

## Configuration

skif reads `skif.toml` or `.skif.toml` only. It does not read `sherif`, `.syncpackrc` or `knip.json`
configuration at lint time; `skif migrate` translates it once into a `skif.toml` (see the
[migration guide](../migrating/)). Rule ids are stable kebab-case names; rules ported from sherif list their sherif
name on the [rules pages](../../rules/).
