skif reads TOML files named `skif.toml` or `.skif.toml`. A root takes the files from its own directory up to the
root of the git repository and merges them (see [Layered configuration](#layered-configuration)). Having both names
in one directory is an error naming both paths. There is no `package.json` key and no JSON, YAML or JavaScript variant, and skif does not read sherif, syncpack or knip
configuration while linting; `skif migrate` translates it once (see the [migration guide](../../guides/migrating/)).
`skif init` writes a starter file and `skif schema` prints its JSON Schema.

Keys are kebab-case, matching rule ids. Unknown keys and wrong types are errors that name the file, line and key.

## Precedence

Defaults, then the files, then the command line (`defaults < files < CLI`). Each layer sets only the keys it
contains, and arrays replace rather than append, except where a key says otherwise (see below). Within the files,
the order is the base of each file from the farthest to the nearest, then `[js.workspaces]`, then package files.
`[[overrides]]` apply on top of the base to the packages and files they select.

## Editor support

`skif init` writes a `#:schema` directive, so editors with Taplo or Even Better TOML validate and complete the
file. Print the schema with `skif schema`.

| `root`, `extends`, `reset` | How files combine |

### `[workspace]`

```toml
[workspace]
ignore-packages = ["examples/*", "!examples/keep"]
package-manager = "pnpm"   # npm | pnpm | yarn | bun; overrides detection
discover-ignore = ["fixtures", "e2e/cases"]   # directories `skif -r` does not search for roots
```

`discover-ignore` takes gitignore-style patterns relative to the directory the run starts in: a bare name matches at
any depth, a pattern with a slash is anchored there, and `!` re-includes. It replaces the default list
(`__fixtures__`, `fixtures`, `__mocks__`, `__snapshots__`); `[]` skips nothing. It is read from the configuration
file that governs the start directory and only affects root discovery in a recursive run.

### `[lint]`

```toml
[lint]
fail-on-warnings = true          # exit non-zero when only warnings were reported
require-ignore-reasons = true    # fail when a suppression has no `reason`, as --require-ignore-reasons does
```

`require-ignore-reasons` makes the suppressions that can carry a `reason` say why they exist: an `[[ignore]]` entry,
also one of an override, and an entry of the `[js]` lists `ignore-files`, `ignore-dependencies`, `ignore-binaries`,
`ignore-unresolved`, `ignore-workspaces` and `ignore-members` and their `extend-` keys, at the top level, per workspace
and in overrides, and the `allow` entries of a rule (`stray-lockfile`, `nested-workspace-root`). `[workspace]
ignore-packages` and `[js] ignore` take plain globs and are not checked. A run with an
entry that has no `reason` fails with exit code 2, naming the entry (``js.ignore-dependencies[1] `left-pad`: no
`reason` ``). The check reads the merged configuration, so the key and position are those of the merged list: an entry
added with `extend-ignore-dependencies` or inherited through `extends` is named by the list it was merged into, and its
name finds it in the files. The key and `--require-ignore-reasons` do the same; either one turns the check on.

### `[rules]`

A rule is a level string, or a table with a `level` and the rule's own options. `severity` is accepted as an alias of
`level`; setting both in one table is an error, and neither name can be a rule option.

```toml
[rules]
unsorted-dependencies = "warn"      # off | info | warn | error
empty-dependencies = "off"
member-toolchain-fields = { level = "error", mode = "match-root" }
unused-exports = { ignore-tags = ["lintignore"] }
```

Rules with options:

| Rule | Option | Values |
| --- | --- | --- |
| `member-toolchain-fields` | `mode` | `forbid` (default) reports every `packageManager` or `engines` field a private member declares; `match-root` allows a field equal to the root's. |
| `stray-lockfile`, `nested-workspace-root` | `allow` | Paths or globs, relative to the workspace root, of files kept on purpose: a string or `{ name, reason }`, matched as a literal path first and then as a glob. An invalid glob, a `!` pattern or `$LOCAL` is a configuration error; an entry that matches no file the rule would report is reported. See [lockfiles and nested workspaces](../../guides/workspaces/#lockfiles-and-nested-workspaces). |
| `stale-patched-dependencies` | `patch-dirs` | Directories, relative to the root, searched for `*.patch` files no `patchedDependencies` entry references. Empty (default) means the directories of the referenced patches and `patches`. |
| `stale-patched-dependencies` | `allowed-patch-paths` | Globs, relative to the root, that every patch file must match (`["patches/**"]`, the paths a build context copies); empty (default) allows any path. |
| `unused-exports`, `unused-types` | `ignore-tags` | JSDoc tag names, without the `@` (a list of strings), that exempt an export. It is read from `unused-exports` and applies to `unused-types` as well. `public`, `beta`, `alpha` and `alias` always exempt, and `alias` also keeps an export out of `duplicate-exports`. |
| `unused-exports`, `unused-types` | `include-tags` | JSDoc tag names; when set, only exports carrying one of them are reported, and only such enum and namespace members (knip's `--tags +name`). A tag named here is judged even when it would exempt (`public`, `beta`, `alpha`, `alias`, `internal` in production mode), so `include-tags = ["public"]` reports the unused `@public` exports; knip reports none of them. |
| `toolchain-pin-drift`, `foreign-package-manager-command` | `kinds` | The kinds of file read at their usual places: `version-files`, `dockerfiles`, `workflows`, `shell-scripts`, `bazel` (the root's `MODULE.bazel`, `WORKSPACE.bazel` and `WORKSPACE`, read for the `pnpm_version` of `pnpm.pnpm(...)` and `npm_translate_lock(...)` and the `node_version` of `node.toolchain(...)` and `nodejs_register_toolchains(...)`; through `files` also `.bzl` and `*.MODULE.bazel` files). Default: `version-files`, `dockerfiles`, `workflows` and `bazel` for `toolchain-pin-drift`, `dockerfiles`, `workflows` and `shell-scripts` for `foreign-package-manager-command`. |
| `toolchain-pin-drift`, `foreign-package-manager-command` | `files` | More files to read, as globs relative to the workspace root (`["deploy/**"]`), whatever their kind. |
| `toolchain-pin-drift`, `foreign-package-manager-command` | `ignore-files` | Files to report nothing in, as globs relative to the workspace root; an entry is a string or `{ name = "...", reason = "..." }`. |

An unknown option is an error that names the rule.

An unknown rule id is rejected with a closest-match suggestion. See the [rules](../../rules/) for ids.

#### Toolchain files

`toolchain-pin-drift` and `foreign-package-manager-command` read the files beside the manifests: in the root and every package directory the version files
(`.nvmrc`, `.node-version`, `.bun-version`, `.tool-versions`, `mise.toml`, `.mise.toml`), Dockerfiles (`Dockerfile`, `Dockerfile.*`,
`*.Dockerfile`, `Containerfile`) and `*.sh`, the last two also in their `docker` and `scripts` subdirectories, and the
root's `.github/workflows/*.yml`. A Dockerfile pins Node with `FROM node:<version>` and Bun with
`FROM oven/bun:<version>`. A file below a directory with a `package.json` that is not a workspace package
belongs to another project and is not read. Every one of these files takes `#` comments, which suppress a finding
there; the reason after `--` is required, and a comment without one suppresses nothing:

```dockerfile
# skif-ignore-next-line toolchain-pin-drift -- the base image is pinned by the platform team
FROM node:18-alpine
# skif-ignore-next-line foreign-package-manager-command -- fallback for the 1.x release branch
RUN npm ci
```

`# skif-ignore-file <rule> -- <reason>` covers the whole file, and a comment without rule ids covers every toolchain
rule. `foreign-package-manager-command` does not report read-only commands (`npm view`, `npm whoami`, `yarn info`) or
a global install of the workspace's own manager (`npm install -g pnpm@9`). See
[ADR 0087](https://github.com/Goldziher/skif/blob/main/adrs/0087-toolchain-pins-outside-package-json-and-the-toolchain-pin-drift-rule.md)
and [ADR 0088](https://github.com/Goldziher/skif/blob/main/adrs/0088-foreign-package-manager-commands.md).

### `[[ignore]]`

Each entry narrows by `rules`, `packages`, `dependencies` and `files`. An empty list does not narrow that dimension, but
at least one list must be set. `files` matches the path of the file a finding is located in, relative to the workspace
root (`src/legacy/**`), as written in every configuration file: unlike the `files` of `[[overrides]]`, it is not
anchored at the file that declares it.

```toml
[[ignore]]
rules = ["types-in-dependencies"]
packages = ["legacy-app"]

[[ignore]]
dependencies = ["left-pad"]
reason = "pinned until the legacy importer is gone"
```

`reason` is optional and records why the entry exists. `--require-ignore-reasons` and `[lint] require-ignore-reasons`
fail a run on an entry without one, and on an entry of a `[js]` ignore list without one, so a baseline of
suppressions can be reviewed and ratcheted down. Entries that flags add are exempt. `skif baseline` writes such
entries for the current findings into a file of their own and keeps it from growing (see the
[CLI reference](../cli/#baseline)).

A `dependencies` pattern of the form `name@specifier` matches only the instances written with that specifier
(`react@^17.0.2`); a bare name matches every version.

### `[policy]`

```toml
[policy]
prefer = "highest"                   # highest | lowest
dependency-types = ["peer"]          # empty means dependencies and devDependencies; name peer or optional to include them
override-reading = "skif"            # skif | syncpack; how resolutions, overrides and pnpm-overrides entries are read
```

`dependency-types` (here and in version and semver groups) names where a version is declared. Each entry may be
negated with `!`:

| Type | Selects |
| --- | --- |
| `prod`, `dev`, `peer`, `optional` | The four dependency sections |
| `local` | A package's own `version` (syncpack's `local`) |
| `resolutions` | `resolutions` of `package.json` (yarn) |
| `overrides` | `overrides` of `package.json` (npm, including nested objects) |
| `pnpm-overrides` | `pnpm.overrides` of `package.json` and `overrides` of `pnpm-workspace.yaml` (syncpack: `pnpmOverrides`) |
| any `[[custom-types]]` name | The versions that custom type reads |

A group that names a type governs it. The catch-all group, and a group that names no type, cover `prod`, `dev` and the
own versions; a type outside those is covered only when `[policy] dependency-types` names it. A `[policy]
dependency-types` list that does not select `local` (`["prod", "dev"]`, `["!local"]`) takes the own versions out as it
takes out the sections it does not name: no dependent is then compared with the `version` of the workspace package it
names, as with syncpack's `--dependency-types prod,dev`. The two are not the same: a list of negations only starts, as
in syncpack, from every dependency section, so `["!local"]` also brings in `peerDependencies` and
`optionalDependencies`; write `["prod", "dev"]` to keep the default sections. syncpack covers every
type by default, so a syncpack configuration that relies on that needs `dependency-types = ["prod", "dev",
"resolutions", "overrides", "pnpm-overrides"]` here. The dependency of an override entry is the package its selector
names (`react@<18`, `parent>react`, `**/react` are `react`); a nested npm object's `.` entry belongs to its parent.
Only string values are instances, and a fix edits the entry in place, in `pnpm-workspace.yaml` for its overrides.
Values that are references rather than versions (npm's `$name`, pnpm's `-`) are skipped, and the `overrides` of
`pnpm-workspace.yaml` are read only when pnpm is the package manager. A group that names no type covers the types
`[policy] dependency-types` governs, so `policy = "banned"` for a dependency does not reach its `peerDependencies`
unless the group names `peer`. Bun reads `overrides` and `resolutions` of the root `package.json`, but ignores
`resolutions` whenever `overrides` is present, even an empty `{}` (checked with Bun 1.4); skif still reads both, so in
a Bun workspace keep the entries in one of the two.

`override-reading` chooses how those entries are read. `"skif"` (the default) is described above. `"syncpack"` reads
them as syncpack 15 does: the key of an entry is the dependency name (`parent@4>child` and `react@<18` are dependencies
of their own, never aligned with `child` or `react`), only string values count (a nested npm object is skipped), and
`pnpm-overrides` is the `overrides` of `pnpm-workspace.yaml` only, so `pnpm.overrides` of a `package.json` is not read.
`skif migrate` writes `"syncpack"` when it migrates syncpack, so a clean syncpack run stays clean.

### `[[version-groups]]`

The first matching group wins. Selectors accept `!` negation, and `$LOCAL` selects dependencies that are
themselves workspace packages.

| Key | Meaning |
| --- | --- |
| `label` | Optional name shown in diagnostics. |
| `dependencies`, `packages`, `dependency-types`, `specifier-types` | Selectors. |
| `policy` | `preferred-semver` (default), `pinned`, `banned`, `ignored`, `same-range`, `same-minor`, `snapped-to` or `semver-range-only` (syncpack's `semverRangeOnly`: versions may differ, and only the range the `[[semver-groups]]` require is checked and fixed). |
| `pin` | Required by `pinned`. |
| `snap-to` | Required by `snapped-to`: packages whose version the group follows. |
| `prefer` | With `preferred-semver`, overrides `[policy] prefer`. |
| `scope` | `manifests` (default) judges what the manifests declare; `lockfile` judges every package `pnpm-lock.yaml` (`bun.lock` in a Bun workspace) resolves, transitive ones included. Only with `banned`. |

```toml
[[version-groups]]
label = "Pin react"
dependencies = ["react", "react-dom"]
policy = "pinned"
pin = "19.1.0"

[[version-groups]]
label = "No moment"
dependencies = ["moment"]
policy = "banned"

[[version-groups]]
label = "No copyleft, not even transitively"
dependencies = ["left-pad"]
policy = "banned"
scope = "lockfile"
```

A path specifier (`link:`, `file:`, `portal:`, `./`, `../`, `/` or `~/`) is never rewritten to a version and never
the version others align with. In a dependency section, while `local-path-dependency` is on, it takes no part in any
version group: that rule reports it, and its fix is the only one the entry gets. With that rule off, and in an
override section or a custom type (which that rule does not read), a path keeps its version-group state without a fix:
next to a workspace package's own version, a path that resolves to the package is valid and one to another directory
is a `version-mismatch`. `banned` groups report a path in every case.

A `scope = "lockfile"` group reports each resolved `name@version` it bans once, at its entry in the lockfile, with
the shortest chain an importer pulls it in through (`importer packages/app pulls it in through mid@2.0.0 >
left-pad@1.3.0`), so removing the `overrides` entry that kept a package out fails the lint. `packages` chooses the
importers by the workspace package they belong to; `dependency-types` and `specifier-types` select manifest entries and
are rejected. The group claims no manifest entry: those fall through to the groups after it. The lockfile is
`pnpm-lock.yaml` in lockfile format 9 (pnpm 9 and 10), or `bun.lock` in a Bun workspace. Without it, with `yarn.lock`,
`package-lock.json` or only Bun's binary `bun.lockb` instead, or when it does not parse, `banned-dependency` reports
that nothing was checked rather than passing.

### `[[semver-groups]]`

```toml
[[semver-groups]]
label = "Libraries use caret ranges"
packages = ["packages/*"]
range = "^"      # one of * ^ ~ > >= < <=

[[semver-groups]]
label = "No range for type packages"
dependencies = ["@types/*"]
ignored = true   # no range requirement; later groups do not apply (syncpack isIgnored / isDisabled)
```

A group sets exactly one of `range` and `ignored = true`.

### `[[custom-types]]`

A field of `package.json` that holds versions. Name it in a `dependency-types` list to select its instances; they
are aligned, pinned, banned and ranged like dependencies, and fixed in place (syncpack's `customTypes`).

```toml
[[custom-types]]
name = "node"                # the token for dependency-types; the dependency name with strategy "version"
path = "engines.node"        # dotted path of keys in package.json
strategy = "version"         # version | name@version | versions-by-name | name~version

[[custom-types]]
name = "package-manager"
path = "packageManager"      # "pnpm@9.15.0": the dependency is pnpm
strategy = "name@version"

[[custom-types]]
name = "runtime"
path = "volta.toolVersion"   # the version
name-path = "volta.tool"     # the dependency name, read from another field
strategy = "name~version"

[policy]
dependency-types = ["prod", "dev", "node", "package-manager", "runtime"]
```

`versions-by-name` reads an object of `name: version`. `name~version` reads the version at `path` and the dependency
name at `name-path`, which only this strategy takes; a fix rewrites the version. A name must not be one of the
built-in types. syncpack's `source` (a custom type read from another file) is not supported.

### `[catalog]`

```toml
[catalog]
mode = "prefer"              # off | prefer | enforce
min-packages = 2             # packages using a dependency before an entry is suggested
exclude = ["typescript"]
report-unused-entries = true  # default false: `unused-catalog-entries` reports nothing unless this is set
```

A `[[version-groups]]` entry whose selectors match a dependency claims it, whatever its policy: the catalog rules
(`catalog-not-used`, `catalog-mismatch`, `catalog-missing-entry`, `unresolved-catalog-references`) leave it to the
group, as syncpack's first-match-wins order does. A `pinned` group for one package (a "baseline") keeps that package
off the catalog while the rest use `catalog:`, an `ignored` group exempts what it matches from the catalog rules, and a
`banned` dependency is reported only as banned. Instances a group claims do not count toward `min-packages`, and the
entry created for a missing dependency takes its version from the instances no group claims. A `catalog:` reference
a group claims still counts as a use for `unused-catalog-entries`. `catalog-mismatch` reports only with `mode = "off"`
and is a warning by default. Semver groups only choose a range and do not claim an instance.

### `[workspace-protocol]`

```toml
[workspace-protocol]
internal = true              # require workspace: for dependencies on workspace packages
allow-local-paths = false    # accept file:/link: paths for internal dependencies
```

The rule is silent for npm and Yarn Classic workspaces, which cannot install the protocol, and for
`peerDependencies`, which a published library names by range. While `local-path-dependency` is on, `file:`/`link:`
paths are left to that rule so one dependency is not reported twice; `allow-local-paths` only decides them when
`local-path-dependency` is off.

### `[[dependency-families]]`

```toml
[[dependency-families]]
name = "babel"
packages = ["@babel/*"]

[[dependency-families]]
name = "react"
enabled = false              # disable a built-in family of the same name

[[dependency-families]]
name = "playwright"          # replaces the built-in family
packages = ["playwright", "playwright-core", "@playwright/test", "@playwright/browser-*"]
scope = "importer"           # manifests (default) | importer | lockfile

[[dependency-families]]
name = "react-types"
packages = ["@types/react", "@types/react-dom"]
scope = "lockfile"
anchor = "react"             # one version of each member per major of react
```

In the default `manifests` scope the members a package declares must share a version. `scope = "importer"` and
`scope = "lockfile"` judge what the lockfile (`pnpm-lock.yaml`, or `bun.lock` in a Bun workspace) resolves instead,
transitive packages included: per importer (what
each workspace package reaches, not following `link:` to other workspace packages) or across the lockfile. Every
resolved member must then be on one version; the lower ones are reported at their lockfile entry. With an `anchor`,
each member may resolve once per major (`@types/react` 17 and 18 next to `react` 17 and 18), and a member on a major
the anchor does not resolve to is reported. No member is exempt in these scopes (the `manifests` scope skips 0.x
members of a released family and floating specifiers). The lockfile is read as for the version groups, and a missing,
foreign or unparseable one is reported.

### `[update]`

Read only by `skif update`, the one command that asks a package registry ([CLI](../cli/#updating)); linting never
does.

```toml
[update]
minimum-release-age = 1440   # minutes a version must have been published before it is proposed; 0 turns it off
max-concurrent-requests = 12 # registry requests at once, at least 1
```

Without `minimum-release-age`, pnpm's `minimumReleaseAge` from `pnpm-workspace.yaml` applies, else one day, as in
syncpack. While a minimum release age applies, a version the registry gives no publish time for is not proposed, and
the report notes it when it would have been the target.

### `[[update-groups]]`

```toml
[[update-groups]]
label = "React moves within its major"
dependencies = ["react", "react-dom"]
target = "minor"             # latest | minor | patch

[[update-groups]]
dependencies = ["@types/node"]
ignored = true               # skif update leaves these alone
```

The first matching group decides (syncpack's `updateGroups`); a group sets exactly one of `target` and
`ignored = true`, and its `target` combines with `--target` so the stricter wins. The selectors are those of
`[[semver-groups]]`. A catalog entry belongs to no package and has no dependency type, so only groups without
`packages` and `dependency-types` apply to it.

### `[format]`

What the [`package-json-format`](../../rules/manifest/#package-json-format) rule and `skif format` check. The rule is
off by default; the table is root-scoped and cannot appear in `[[overrides]]`. The defaults are syncpack's, except
`sort-exports`.

```toml
[format]
sort-first = ["name", "description", "version", "author"]   # top-level keys that come first, in this order
sort-packages = true          # the remaining top-level keys in byte order; false keeps their order
sort-az = ["bin", "contributors", "dependencies", "devDependencies", "keywords", "peerDependencies", "resolutions", "scripts"]
sort-exports = ["types", "default"]   # types first, default last, every other condition where it is
format-bugs = false           # { "url": "..." } becomes "..."
format-repository = false     # { "type": "git", "url": "git+https://github.com/o/r.git" } becomes "o/r.git"
# indent = "  "               # unset: keep each file's layout
```

`sort-az` sorts each named field one level deep: an object by key, an array of strings by value; `a/b` names a nested
field. It is for fields whose order means nothing: an array with a `!`-prefixed entry, such as `files` with a negated
glob, keeps its order, because a negation only excludes what the patterns before it matched. `sort-exports` orders the keys of every object in `exports` (the others keep their order) and always puts
`default` last. Node and bundlers take the first condition that matches, so only `types` first and `default` last
cannot change how an import resolves; that is the default, and its fix is safe. A list that reorders other conditions,
such as syncpack's default `["types", "node-addons", "node", "browser", "module", "import", "require", "svelte",
"development", "production", "script", "default"]`, is applied with an unsafe fix (`skif format --unsafe`,
`skif --fix-unsafe`). `format-bugs` and `format-repository` collapse only an object the shorthand holds completely:
a `bugs` with an `email`, or a `repository` with a `directory` or a `type` other than `git` (`svn`, `hg`), stays. An
empty list turns its step off. Sorting is by byte order, the order `unsorted-dependencies` uses.

Without `indent`, formatting moves members with their own text and keeps every file's whitespace, and whitespace is
never reported. An object or array with a comment between its members is not reordered, and a `bugs` or `repository`
with a comment inside is not collapsed, so a comment never ends up beside another member or disappears. With `indent` (spaces or tabs; `"\\t"` is read as a tab), a manifest must be laid out as
`JSON.stringify(manifest, null, indent)` lays it out, with the file's own line ending and a final newline. A manifest
that is not strict JSON (comments, trailing commas, single-quoted strings) keeps its layout, because laying it out again
would drop its comments or write invalid JSON. Only `package.json` files are formatted.

### `[js]`

```toml
[js]
enabled = true
entry = ["src/index.ts", "src/server.ts!"]
project = ["src/**/*.ts"]
ignore = ["**/*.generated.ts"]
ignore-files = ["scripts/one-off/**"]
ignore-dependencies = ["@types/node", "/^@org\\/.+$/"]
ignore-binaries = ["docker"]
ignore-global-binaries = true
ignore-unresolved = ["#internal/*", "/^virtual:/"]
ignore-workspaces = ["tools/*"]
ignore-members = ["/^_/"]
ignore-exports-used-in-file = { type = true, interface = true }
production = false
include-entry-exports = false
tsconfig = "tsconfig.app.json"
use-tsconfig-files = false
include-fixtures = false
use-public-hoisting = false
discovery = "auto"

[js.cycles]
allow = [["src/a.ts", "src/b.ts"]]
dynamic-imports = false

[js.workspaces."."]
ignore-dependencies = ["rimraf"]

[js.workspaces."packages/web"]
entry = ["src/main.tsx"]
ignore-unresolved = ["virtual:*"]
include-entry-exports = true
paths = { "@/*" = ["./src/*"] }

[js.workspaces."packages/web".plugins]
vite = { config = ["vite.web.config.ts"] }

[js.plugins]
vitest = true
jest = { enabled = true, config = ["jest.config.cjs"] }

[js.compilers]
html = { imports = ['<script[^>]+src="([^"]+)"'] }
page = { as = "mdx" }
```

`enabled` defaults to `true`, so a plain `skif` run checks everything; the git hooks pass `--no-js`. Per-workspace
tables, keyed by directory (a glob such as `packages/*` works, an exact key wins over a glob, and `"."` is the root
workspace; `*` stops at `/`, so `packages/*` does not select `packages/a/nested`, and when several glob keys select a
directory the first in file order wins), take `entry`, `project`, `ignore`, `ignore-files`, `ignore-dependencies`, `ignore-binaries`,
`ignore-unresolved`, `ignore-members`, `ignore-exports-used-in-file`, `include-entry-exports`, `paths` and `plugins`,
plus `extend-ignore`, `extend-ignore-dependencies`, `extend-ignore-binaries` and `extend-ignore-unresolved`, which
append to the list the table inherits through `extends`. A plugin entry is
`true`, `false` or a table with `enabled`, `config`, `entry` and `project`; the plugin names are checked, and a
misspelt one is a configuration error with the closest name suggested. The `"."` table adds to the top-level ignore
lists and replaces its `entry` and `project`.

**Ignore lists.** `ignore-dependencies`, `ignore-binaries`, `ignore-unresolved`, `ignore-members` and
`ignore-workspaces` take exact names, globs (`@types/*`) and regular expressions. An entry is a regular expression
when it is written between slashes with optional flags (`/^@org\/.+$/`, `/^vite/i`), or, as in knip, when it contains
`+`, `\`, `(`, `)`, `|` or `^`, contains `.*` or `.+`, or ends in `$`. A regular expression is not anchored and matches
anywhere in the name. This differs from knip, which also treats `*` and `{` as regular expression syntax; skif keeps
them for globs so that `@types/*` means what it says, and an entry such as `eslint-*` is a prefix glob here but a
regular expression in knip (where it also matches `my-eslint-x`). Regular expressions are compiled by the Rust `regex`
engine, not by JavaScript: look-ahead, look-behind and back-references (`/^(?!@types)/`) are configuration errors,
`\d` and `\w` are Unicode aware, and the flags `i`, `m` and `s` apply while `g`, `u`, `y` and `d` are accepted and
ignored. `skif migrate` copies a knip pattern as written, so run `skif` once afterwards: an unsupported pattern is
reported with the compiler's message. A pattern that does not compile is a configuration error. An entry ending in
`!` applies in production mode only (`"left!"`).

**Reasons on ignore entries.** Every ignore list (`ignore-files`, `ignore-dependencies`, `ignore-binaries`,
`ignore-unresolved`, `ignore-members`, `ignore-workspaces` and the `extend-` keys, at the top level, in
`[js.workspaces."<dir>"]` and in the `js` of an override) takes an inline table in place of a string, so the entry
records why it exists:

```toml
[js.workspaces."packages/app"]
ignore-dependencies = [
  "left-pad",
  { name = "some-loader", reason = "false positive: loaded by the bundler from a config string" },
]
```

`name` holds what the string form holds (a name, a glob or a slash-delimited regular expression, with the `!`
production marker), and `reason` is optional. The two forms mix in one list and match the same. A blank `reason` is a
configuration error, and `--require-ignore-reasons` or `[lint] require-ignore-reasons` fails a run on an entry without
one. `stale-js-config` reports a table entry that matched nothing by its `name`.

**`ignore-unresolved`** lists import specifiers that are never reported by `unresolved-imports` or `stale-mocks`, at the
top level and per workspace. `ignore-dependencies` also silences both for a matching specifier, because plugins
declare virtual modules through it; use `ignore-unresolved` for your own. Two small differences from knip remain:
an unresolved import is located at the start of its statement, not at the specifier, and `import "./dir"` of a
directory with neither an index file nor a `package.json` is reported where knip is silent. A directory with a
`package.json` whose `main` or `exports` point at build output that does not exist resolves to the source file behind
it (`dist` to `src`), and is not reported when there is none. A relative import of a missing file that a `.gitignore`
lists (also as `./dir` for an ignored `dir/index.ts`, or without its extension) is taken for generated and not
reported: the `.gitignore` of the root, of a package, or of any directory between the file and the git repository
root, such as a `src/temp/.gitignore` that ignores its own contents or the `.gitignore` of a folder above a nested
root. So is one that names an ignored path below another `rootDirs` directory of the nearest `tsconfig.json` that is
not generated yet (`./+types/root` of a React Router route, from `.react-router/types`), SvelteKit's `./$types`
while the `.svelte-kit/tsconfig.json` that the nearest `tsconfig.json` or `jsconfig.json` extends, directly or through
another config, is missing and gitignored (once `svelte-kit sync` has written it, its `rootDirs` decide: a route type
is not reported while the ignored `.svelte-kit/types` is missing too, and is reported once that directory exists
without it), a root-relative import of a JSON or other non-code file (`import logo from "/vite.svg"`, served from the
bundler's public directory), and a `#` specifier unless the nearest `package.json` declares `imports`. Since the
generated module may import any source file beside it, those files are reached and their exports count as used: the files of the ignored file's directory, of an ignored directory and below it, or, for the ignored
index of a directory (`src/migrations/sqlite/index.ts` named as `./migrations/sqlite`), of the directory holding that
directory and below it (`src/migrations/**`), within the importing package. When those files would be the package
directory or its `src` (an ignored `src/schema.gen.ts`, or `src/generated/index.ts` named as `./generated`), none are
credited, since that would hide most of the package's unused files.

A `require()` or `import()` of a template literal with a relative static prefix (`` import(`./reporters/${name}.js`) ``)
reaches every file matching the prefix, `*` for each substitution, and the suffix, as `import.meta.glob` does, and their
exports count as used; an output extension also matches the sources it is built from (`.js` matches `.ts` and `.tsx`).
Paths built at runtime in other ways are not followed: a specifier held in a variable, a `fast-glob` or `glob` call
listing files relative to `__dirname`, or a registry that loads `${name}/${name}.module.js` from a directory it computes.
Add such files to `entry`.

**`ignore-workspaces`** lists workspace directories (globs) the JavaScript analysis skips. Unlike `[workspace]
ignore-packages`, the packages stay in the workspace, so manifest and policy rules still check them. The root is never
skipped. Entries match directories, so `*` stops at `/`: `packages/*` skips `packages/a` but not `packages/a/nested`
(use `packages/**` for both), as in knip.

**`[js.compilers]`** reads the files of an extension skif has no reader for, keyed by the extension without its dot.
It is the static counterpart of knip's `compilers`: knip runs a function that turns the file into JavaScript, skif runs
no project code and takes one of two declarations instead.

- `imports`: regular expressions, each with exactly one capture group, matched against the whole text of the file.
  Every capture is an import specifier, resolved as an import written in that file (`./src/main.ts` from the file's
  directory, `lit` as a package), so a missing file is reported by `unresolved-imports` and a package the manifest does
  not list by `unlisted-dependencies`. The imports bring in no names, like `import "./x"`. The patterns are compiled by
  the Rust `regex` engine (no look-around or back-references); `(?:...)` groups do not count as capture groups.
- `as`: read the files with the reader of one of skif's own extensions, as if they had it: `js`, `mjs`, `cjs`, `jsx`,
  `ts`, `mts`, `cts`, `tsx`, `vue`, `svelte`, `astro`, `mdx`, `marko`, `tsrx`, or a stylesheet extension (`css`,
  `scss`, `sass`, `less`, `pcss`, `styl`, `stylus`).

The files of a declared extension join the default `project` (`**/*.html`), so one that no entry reaches is reported
by `unused-files`; a `project` that leaves the extension out leaves them unjudged. They are modules for every other
purpose too: an import of one (`import "./intro.page"`) follows it, and `project-extension-unregistered` does not
report the extension. A file that only a tool loads, such as an `index.html` no bundler plugin reads, needs an `entry`
pattern. A declaration for an extension skif reads itself (`vue`), an extension written with its dot or in upper case,
an entry with both or neither of `as` and `imports`, an unknown reader, an empty `imports` list and a pattern that
does not compile or has not exactly one capture group are configuration errors. The table applies to the whole root:
it cannot be set per workspace or in an override, and a nearer configuration file replaces an extension's entry as a
whole.

```toml
[js.compilers]
# <script type="module" src="./src/main.ts"></script>
html = { imports = ['<script[^>]+src="([^"]+)"'] }
# Tailwind directives in a stylesheet extension skif does not know
tw = { as = "css" }
```

**`entry` and `project`.** As in knip, a pattern ending in `!` is a normal pattern in a normal run. In a production run
only the patterns ending in `!` count and the others are excluded; when none ends in `!`, the defaults apply. The
entries that do not end in `!` are also removed from the project, so a file only they reach (`scripts/*.ts` next to
`src/index.ts!`) is not reported as unused, and the files that tools add to the project are removed as well.

**Incomplete entries.** When skif cannot know all the entry files of a package (a tool configuration it cannot read
statically, or a published `main`, `exports` or `bin` that maps to no source file), a file no known entry reaches may
still be one. A published path that names nothing at all (no file, no source behind it, not in a build output
directory, not ignored by git and not in a `bin` directory a build step of the package may write, such as a stale
`bin/cli.js`) is not one of them: it is no entry, `stale-js-config` reports it (`package-entry`) and the package is
judged from its other entries. `unused-dependencies` and `unused-dev-dependencies` then skip the package: an unread
configuration may name a package by string (a test environment, a coverage provider, a reporter). `unused-exports`,
`unused-types`, the namespace export rules and the member rules skip the files that may be unknown entries: the
whole package, or only the files of the narrowed scope described below, and `explain-usage` gives their exports the
verdict `not-judged`.

`unused-files` skips only the files the unreadable configuration could plausibly make entries, its narrowed scope. A
config that is unknown, spreads or merges in an unknown base, or computes its entry keys can only add entries where its
tool looks for them:

| Plugin | Narrowed scope (relative to the package, besides the plugin's own entry globs) |
| --- | --- |
| `next` | `{,src/}{app,pages}/**` and `{,src/}{instrumentation,instrumentation-client,middleware,proxy}.*`: the router may take other extensions there |
| `vite` | `{,src/}{index,main}.*`, the conventional build input a shared base config may set |
| `vitest`, `playwright` | test files, test and fixture directories (`test`, `tests`, `__tests__`, `__mocks__`, `__fixtures__`, `e2e`, `spec`, `specs`, `fixtures`, `mocks`, `testing`, `test-utils`), files whose name contains `setup` or `teardown`, and files named `*.{test,spec,bench,e2e,integration}*` |
| `storybook` | for an addon, `framework` or `core.builder` whose package is not known statically, the Storybook config directory (`.storybook/**`, `.rnstorybook/**`), where a local addon lives; the package's dependencies are not judged |

A config in an Nx project directory without a `package.json` (see [Nx workspaces](../../guides/workspaces/#nx-workspaces))
hides entries only in that project: the scope above is taken relative to the project, and a config that gives no scope
leaves the project's files unjudged (`<project>/**`) rather than the whole package's. Nx's root `jest.config.ts`
(`projects: await getJestProjectsAsync()`, or `getJestProjects()`, from `@nx/jest` or `@nrwl/jest`) is not incomplete:
its projects are the Jest configs of the Nx projects.

The files in the scope are treated as entries, so what they import is not reported either: those outside the package's
`project` globs too, and, for a scope of a package with workspace packages below it (a root test config), the matching
files of those packages. Every other file of the package is judged as usual, its unused exports, types and members
included, since whatever an unknown entry in the scope imports is already counted. The exports of a file in the scope
are not judged, even with `include-entry-exports`, as the tool may read them. The whole package stays unjudged when the
configuration does not parse (an `esbuild` build script that exports nothing is read for every `entryPoints` it writes,
and counts as unparsable only when it writes none), when a `vite` config computes `root`, `build.rolldownOptions.input` (Vite 8),
`build.rollupOptions.input` or `build.lib.entry` itself or is unknown as a whole (a key is computed by the config itself when an unknown spread inside
it, or above it of a value the config computes, such as `build: { ...makeLib() }` with `makeLib` declared in the config,
may set it; a spread of an imported base is shared and narrows), when a `vitest` config computes `root`, `test.include`,
`test.setupFiles`, `test.globalSetup` or a `test.reporters` name itself or is unknown as a whole, when a `playwright`
config is unknown as a whole or computes its `reporter` list itself (a reporter's name is not known statically, or a
spread of a value the config computes may set the list: a reporter module may be any file; a reporter a condition picks
among known ones, `process.env.CI ? 'github' : './reporter.ts'`, credits each), when a `storybook` config is unknown
as a whole or spreads an unknown value, when the plugin gives no scope (any other plugin), when the published build
output maps to no source file
(publishing may expose any file), and when a module of the package imports a computed path (`import(name)`,
`require(name)`), which may load any of its files. `explain-usage` says which applies: a file in the scope is an entry
of kind `incomplete-scope`, a file outside it reported by `unused-files` names the scope, and a file of a package left
unjudged as a whole is `entries-incomplete`.

A file that a relative import reaches through the `rootDirs` of the importer's `tsconfig.json` (code generated into a
build output tree such as `bazel-bin/packages/app`) belongs to the importing file's package when it lies in no workspace
package's directory and is not a source file skif lists (build output that git ignores), and so do such files it imports
by relative paths below the same root directory: their imports are judged against that package's dependencies, which
Node.js resolves them from. A file of a workspace package always stays that package's, and the root's `ignore` globs
still apply to an adopted file.

In a Bazel repository (the nearest directory at or above the workspace root, within the git repository, with a
`MODULE.bazel`, `REPO.bazel`, `WORKSPACE.bazel` or `WORKSPACE`), the output trees behind the `bazel-*` links at its top
(`bazel-bin`, `bazel-out`, `bazel-testlogs`, `bazel-<workspace>`) are never read: their contents are whatever the last
build left, for whichever configuration. An import that reaches a file there, through `rootDirs` or otherwise, is of
generated code and is not followed, so no finding is located in them. A relative import of a missing file is not
reported when the nearest `BUILD.bazel` or `BUILD` file at or above the file's directory declares it as an output:
it is a literal of the `outs`, `out` or `stdout` of a target there (`js_run_binary(outs = ["src/gen/schema.js"])`),
also with another extension or none, or lies below one of its `out_dirs` or `out_dir`. Bazel builds it into
`bazel-bin` beside the package. A `rootDirs` directory below `bazel-bin` does not make a missing import generated,
built or not; the `BUILD` files decide, so an import that none declares is unresolved whatever was built. The
dependencies of the generated code are those its target names (see the `bazel` plugin below).

**`paths`** is a `tsconfig`-style map for one workspace, `{ "alias/*" = ["./target/*"] }`, targets relative to the
workspace directory. Each target is tried as a module alias ahead of the aliases tools declare.

**`tsconfig`** names the TypeScript configuration of the root package, relative to the workspace root, which is read
in place of its `tsconfig.json`: its `paths`, `baseUrl` and `rootDirs` resolve the imports of the root package's
files (and of directories below the root that have no config of their own), its `compilerOptions` decide which
`@types` packages and JSX runtime count as used, and the `typescript` plugin reads it too. Other packages keep their
own `tsconfig.json`. The path must stay inside the workspace root (no absolute path, no `..` above it), and the
command line refuses a path that names no file in the root whose configuration sets it. This is knip's `--tsConfig`,
which `skif --tsconfig` overrides. It can only be set at the top level.

**`use-tsconfig-files`** takes the project files of each package that has a `tsconfig.json` (for the root, the
`tsconfig` above) from it, as knip's `--use-tsconfig-files` does: the files its `files` and `include` select (every
file when it sets neither), followed through `extends` and through the `references` that lie below it. As in
TypeScript, `exclude` and `compilerOptions.outDir` filter only what `include` selects, never the files `files` names.
These replace the `project` globs and the globs plugins add; entry files are unchanged, and production mode still
leaves test files out. Patterns that leave the package directory are ignored, and the `exclude` of a referenced config
applies to what the `include` of all of them selects. Packages without a `tsconfig.json` keep their `project` globs.
The command line warns on stderr about a `tsconfig` that selects no file of its package, which leaves that package
without project files.

**`ignore-exports-used-in-file`** is `true`, or a table of the kinds `variable`, `function`, `class`, `enum`,
`namespace`, `type` and `interface`: an export that the same file references is then not reported. skif does not tell
type aliases from interfaces, so `type` and `interface` are the same switch. `member` is accepted; members read in
their own file always count as used. **`ignore-members`** lists enum and namespace member names never reported by
`unused-enum-members` and `unused-namespace-members`. A member is also exempt when its own JSDoc carries a tag that
exempts an export (`@public`, `@beta`, `@alpha`, `@alias`, `@internal` with `production`, or an `ignore-tags` name).
**`include-entry-exports`** may be set per workspace.

**`ignore-files`** lists globs of files that `unused-files` never reports, at the top level (relative to the workspace
root) and per workspace (relative to its directory), like knip's `ignoreFiles`. Unlike `ignore`, every other rule still
analyses them.

**`[js.cycles]`** configures `circular-imports` (off by default), like knip's `cycles`. `allow` lists cycles that are
not reported, each as the list of its files relative to the workspace root (`./` is optional): skif reports a cycle as
the set of modules that import each other, so an entry allows the cycle whose files are exactly its files, in any
order; an empty entry or an empty path is a configuration error. `dynamic-imports = true` counts `import()` as an
edge; by default only static value imports do, and type-only imports never do.

**`stale-js-config`** (a warning) reports `ignore-dependencies`, `ignore-binaries`, `ignore-unresolved` and
`ignore-workspaces` entries that matched nothing in the run, `[js.workspaces]` keys that select no package, and `entry`,
`project` and `ignore` patterns (top level and per workspace) that match no file, like knip's configuration hints
(`entry-empty`, `project-empty` and stale `ignore`). A pattern is reported only when it matches neither a file the
analysis knows nor any file on disk, gitignored or not and of any extension, so `ignore = ["dist/**"]`, `ignore =
["**/*.json"]` and `entry = ["index.html"]` are not reported while such files exist; the disk check skips `node_modules`
and `.git` unless the pattern names them. A pattern of a workspace glob key such as `packages/*` is reported once, under
the key as written, when it matches in none of the packages the key selects. Negated patterns and patterns that leave
the package (`../`) are not judged. An `ignore-files` pattern is reported when it hides no file `unused-files` would
report and matches no file on disk (while that rule runs). `[rules] stale-js-config = "error"` is knip's
`--treat-config-hints-as-errors` (`skif migrate` writes `warn` unless `--strict-hints` is given). An
`ignore-dependencies` or `ignore-unresolved` entry is not judged when a rule that consults it is off. The
`ignore-dependencies` list of a package whose entry files skif cannot determine is not judged; the global list is judged
over the other packages, and an entry that matches a dependency such a package lists is never called stale. In a
multi-root run, a finding about a configuration file several roots read (a `--config` file, or a file above them) is
reported once, at the highest severity among the copies the run shows, and an entry of its lists only when every root
that judged it found it stale: a root that used it silences it, and a root that could not judge it (a rule off, entry
files it cannot determine) has no say. Each package a `[js.workspaces]` glob table selects has a list of its own, so
one package's use of an entry does not silence it for another. The decision is made over what the run shows, after
`--fix` and after `--workspace`, `--include` and `--exclude`: a copy those flags leave out of the run does not raise
the severity of the one reported. It also
reports knip's tag hints: an `ignore-tags` tag, or `@internal` with `production`, on an export or member that is used
anyway (while `unused-exports` runs). A tag on an enum or namespace that hides an unused member is needed and not
reported. The tag hints cover the files whose exports `unused-exports` judges, so in a package with incomplete entries
narrowed to a scope they cover every file outside it.

The rest of knip's configuration hints are part of `stale-js-config` too:

- `entry-redundant`: an `entry` pattern that is a plain path to a file a plugin, the manifest (`main`, `exports`,
  `bin`, ...), a tool configuration or a script already makes an entry. With `include-entry-exports`, only plugin entry
  globs and the manifest count, since a configured entry has its exports judged.
- `project-redundant`: a `project` pattern that is a plain path to an entry file, which is always in the project. Not
  judged with `use-tsconfig-files`.
- `entry-top-level` and `project-top-level`: the top-level `entry` or `project` in a workspace with several packages,
  where they apply to the root package only; move them to the `[js.workspaces]` table they are meant for.
- `project-extension-unregistered`: a `project` pattern selecting an extension skif does not analyse (`*.json`).
  Stylesheets (`.css`, `.scss`, `.sass`, `.less`, `.pcss`, `.styl`, `.stylus`) are not reported: skif reads their
  imports, so a knip `project` glob such as `src/**/*.{ts,css}` keeps working unchanged. Neither are the extensions
  of `[js.compilers]`.
  `project-extension-excluded`: `project` patterns that name extensions but not `.vue`, `.svelte` or `.astro` while the
  package has such files, which then leave the project. knip ties both to its compilers; skif reads those component
  files without one, so the second is judged by the files present instead.
- `package-entry`: a path in `main`, `module`, `browser`, `bin`, `types`, `typings` or `exports` that names no file,
  neither itself nor a source file behind it. Paths a `.gitignore` hides, paths in a build output directory (`dist`,
  `build`, `lib`, ..., whatever the extension; knip reports these unless gitignored) and paths into a listed dependency are not judged. It points
  at the field in `package.json`. A path in a `bin` directory in any published field (`"bin": "bin/cli.js"`, but also
  `"main": "bin/cli.js"`) that names no file is reported too, and since it loads no code it does not make the
  package's entries incomplete; a root `"bin": "cli.js"` was always reported, and a path in `dist/...` still is not.
  A `bin` path is not judged when a build step of the package may write it: a `build`, `build:*`, `prepack` or
  `prepublishOnly` script, a script that runs a compiler or bundler (`tsc`, `tsup`, `tsdown`, `esbuild`, `rollup`,
  `rolldown`, `webpack`, `rspack`, `rslib`, `unbuild`, `ncc`, `babel`, `swc`), a bundler configuration a plugin reads
  (`tsup.config.ts`, `rollup.config.mjs`, ...), or a `tsconfig` `outDir` at or inside `bin`. When the only build
  steps run the TypeScript compiler (`tsc`, `tsgo`, without `--outFile`), the path is judged unless a file of the
  package has its name (`stack.ts` for `bin/stack.js`), also when a `.gitignore` hides it (`*.js`): the compiler names
  each output after a source file, so a `bin/stack.js` no source is named after is a path into nothing. Ignored paths count
  with the ignore files from the root of the git work tree down, also above the analysed root, and
  `.git/info/exclude`; the global excludes file (`core.excludesFile`) is not read.
- `top-level-unconfigured` and `workspace-unconfigured`: more than 20 unused files that are more than a fifth as many
  as the files the analysis reached suggest missing entries, with knip's thresholds. A single-package workspace gets one hint; otherwise
  each package with more than one unused file gets one, largest first.

**Where binaries are run.** `unlisted-binaries` reads the commands of the `package.json` scripts, the commands that
plugins read from the files of their tools (workflow steps of `.github/workflows`, Git hooks, `lint-staged` tasks and
the other configs that hold commands) and the literal commands that source files reachable from an entry run through
`node:child_process` (`exec`, `execSync`, `spawn`, `spawnSync`, `execFile`, `execFileSync`), `execa`, `zx` and
`nano-spawn`. A binary of a script is reported at the script in `package.json`; one of any other command at the file
that holds the command. A binary fetched on demand (`npx x`, `pnpm dlx x`) is never reported, and a command whose
arguments are computed is not read. A specifier `.bin/x`, `node_modules/.bin/x` or `./node_modules/.bin/x`, in
`require.resolve`, `import.meta.resolve` or any other import, names the link of binary `x`, which code looks up to spawn
it: it uses the dependency that provides `x`, whether or not it is installed, is reported at the file when no dependency
provides `x`, and is never an `unresolved-imports` finding. The steps of CI workflows, Git hooks and task runners run on
machines that bring their own tools, so a binary they run by name is never reported there; one they run through a
package manager (`pnpm exec x`, `yarn x`) or a `node_modules/.bin` path is, as knip does. A GitHub Actions step whose
`shell` is not a POSIX shell (`pwsh`, `cmd`, `python`) is not read. The binary of a workspace member is provided where
the package manager puts it on the `PATH`: with npm, Yarn Classic, hoisted pnpm and hoisted Bun, which link every
member's binaries into the root `node_modules/.bin`, for every package; with isolated pnpm, npm with
`install-strategy=linked` in the root `.npmrc`, Yarn Berry, isolated Bun and in a Rush repository only for the packages
that list the member and for the member's own scripts. pnpm is hoisted with
`nodeLinker: hoisted` in `pnpm-workspace.yaml`, or without a `nodeLinker` there with `node-linker=hoisted` in the root
`.npmrc` only before pnpm 11 (pnpm 11 reads its linker only from `pnpm-workspace.yaml`; without a pnpm version in
`packageManager`, `.npmrc` is read). Bun is isolated with `linker = "isolated"` under `[install]` in the root
`bunfig.toml`, or without a `linker` when `bun.lock` records `configVersion` 1. In a Rush repository (a `rush.json` at
the root), `rush`, `rushx` and `rush-pnpm` are Rush's own commands and never unlisted.

**Scripts that change directory.** A `package.json` script command after `cd <dir>` or `pushd <dir>` (until `popd`),
and one that `npm --prefix <dir> exec`, `pnpm -C <dir> exec` (`--dir`) or `yarn --cwd <dir> exec` runs, runs in that
directory: the files it names are relative to it, and when the directory is in another workspace package, the binaries
it runs and the packages it loads are credited to that package, as for `pnpm --filter <name>`. A binary that package
does not provide either is reported at the script, naming the package it runs in (``script `a` runs `x` in
`packages/web`, which no dependency of `web` provides``), unless a package manager runs a script of that name there
(`cd web && pnpm bundle`). When the directory is in a project of its own instead (a directory below the package with a
`package.json` that is no workspace member, such as a nested root of `skif -r`), a binary run there is judged against
that project's manifest: a provider it lists is used, and `skif -r` credits it to that root; otherwise one of the
package holding the project may provide it, else it is reported, naming the project. In a directory of the package
itself or of no package or project, a command after `cd` stays a command of the script's package and one a directory
flag runs is not judged, as before. The binaries and packages that a workflow step, a tool config's command or a
source file run and load after `cd <dir>` (`run: cd sub && pnpm exec rspack`, `run: cd sub && node -r hook x.js`) are
placed the same way, with the directory relative to the package where the command starts (the workspace root for a
workflow), and are not credited where the command starts. A binary such a command runs by name where its tool
does not judge one (a workflow step), or fetches on demand, is only a credit there. A step's `working-directory`, its
own or the `defaults.run` of its job or workflow, is read as a `cd` before the step. In a workflow step,
`$GITHUB_WORKSPACE`, `${GITHUB_WORKSPACE}` and `${{ github.workspace }}` are the workspace root, so
`cd $GITHUB_WORKSPACE/sub` and a `working-directory` of `${{ github.workspace }}/sub` are followed. A script that a
package manager runs in another directory (`cd web && npm run build`) is the script of the package there, so the caller's script of that name is not followed.
A `cd` in a subshell
(`(cd "$TMP" && tar xf a.tgz) && npm run build`) ends with it. A directory that is not a static relative path
(`cd $DIR`, `cd /tmp`, `cd -`, `cd "$(dirname "$0")"`) is not followed: a binary run by name there is judged where the
script starts, but a package manager run there (`npm run build`, `bun run build`, `pnpm exec rspack`) works on the
package of that directory, as with `--filter`, so its scripts are not followed and its binaries are not judged. A
command that a source file runs with a `cwd` option (`execa('bun', ['run', 'build'], { cwd })`,
`execSync('npm run build', { cwd })`) runs in such a directory, unless the `cwd` names the directory the call runs in
anyway (`process.cwd()`, `'.'`, `undefined`), which changes nothing, or the file's own location computes it
(`__dirname`, `import.meta.dirname`, `path.join(__dirname, '../sub')`), which runs the command in that directory below
the file. knip judges these commands at the script's own package.

**`ignore-global-binaries`** (default `true`, top level only) keeps `unlisted-binaries` quiet about the system and
platform tools scripts run (`rm`, `curl`, `git`, `docker`), which are installed globally, like knip's
`ignoreGlobalBinaries`. The Bazel launchers `bazel`, `bazelisk` and `ibazel` count as such tools too, while a listed
`@bazel/bazelisk` or `@bazel/ibazel` is still used by the scripts that run them. Set it to `false` to report each one
that no dependency provides, unless `ignore-binaries` lists it. Shell builtins (`cd`, `echo`, `export`), shells, pass-through commands (`env`, `sudo`, `xargs`), the package
managers and `node` are never reported.

**`use-public-hoisting`** (default `false`, top level only) counts a package that the install hoists publicly into
a `node_modules` above a package as available to it, so a file that imports it without listing it is not reported by
`unlisted-dependencies`. Off, skif reports such an import as knip does; `ignore-dependencies` (or
`--ignore-dependency`) quiets one package instead. On, skif reads:

- pnpm's `publicHoistPattern` and `shamefullyHoist` from `pnpm-workspace.yaml`, else `public-hoist-pattern` and
  `shamefully-hoist` from the top level of the root `.npmrc`, which pnpm 11 no longer reads for these settings (so
  `.npmrc` is skipped when the root's `packageManager` names pnpm 11 or later). The patterns hoist into the root
  `node_modules`, so they apply to every package. `*` matches any run of characters, a `!` pattern excludes what the
  patterns before it include, and `shamefully-hoist = true` is the pattern `*`. Without a setting nothing is hoisted:
  pnpm's default, which changed in pnpm 10, is not assumed. Rush repositories are not read.
- `public_hoist_packages` of rules_js's `npm_translate_lock`, in the Bazel repository root's `MODULE.bazel`,
  `WORKSPACE.bazel` or `WORKSPACE`, when it is a dict literal: each key (a version suffix such as `@1.2.3` dropped)
  is available to the packages at or below each Bazel package its list names, `""` being the repository root.

```toml
[js]
use-public-hoisting = true
```

with `public-hoist-pattern[]=hoisted-only` in the root `.npmrc`, or
`npm_translate_lock(..., public_hoist_packages = {"hoisted-only": [""]})`, makes `import 'hoisted-only'` in any
package no unlisted dependency. The setting changes no `unused-dependencies` finding: a package a manifest lists is
used or unused as before, whether it is hoisted or not. Strict mode (`--strict`) ignores it, since every package
there uses only its own manifest. `node-linker=hoisted` and the flat layouts of npm, Yarn Classic and Bun are not
counted: they make every installed package resolvable everywhere, so counting them would amount to turning
`unlisted-dependencies` off. Binaries are not affected: a hoisted package's binary is still credited only to a
package that lists it.

`discovery` chooses how source files are found. `auto` (the default) and `walk` walk the directories, which finds
every untracked file. `git` lists the files from the git index when the analysed root is in a git work tree and checks
each directory with one `stat` instead of walking it: a directory modified at or after the time the index was written
(equal counts as modified) is listed from disk, so new untracked files and directories, plugin config files that were
never `git add`ed and deleted files are found and dropped as the walk finds and drops them, and an untouched directory
is listed from the index without an `opendir`. One case is invisible to `git`: an untracked file created before the
last rewrite of the index (a `git add` or `git commit` of another file, or a `git status` that refreshes it) in a
directory nothing has touched since. That is why `auto` does not use the index: such a file is the entry or the only
importer of a file that would then be reported as unused. `git` suits a fresh checkout, as in CI, and its
`unused-files` findings offer no fix that deletes the file ([ADR 0095](https://github.com/Goldziher/skif/blob/main/adrs/0095-untracked-files-member-manifest-errors-and-converging-fixes.md)). `git` falls back to
the walk when there is no usable index: a repository outside git, a split or sparse index, a SHA-256 repository
(`extensions.objectformat`), or an index whose SHA-1 checksum does not match (an index written with `index.skipHash`,
which `feature.manyFiles` sets, is read without the check, so a torn read of an index that is being rewritten is then only
caught by the reader's bounds checks). A file the index lists but that is missing on disk is never
reported. The `.gitignore` rules, hidden directories and `[js] ignore` apply to the listing as they apply to the walk.
The rules that list directories for files workspace discovery does not read, the toolchain scan (version files,
Dockerfiles, shell scripts, workflows and the `files` globs) and the search for the Bazel `BUILD` files of
`stray-lockfile`, list through the same index listing under `git`, so they share its speed and its blind spot
([ADR 0121](https://github.com/Goldziher/skif/blob/main/adrs/0121-one-git-index-listing-for-every-provider.md)).

A dependency counts as listed when the package's own `package.json`, the `package.json` of a package that contains
it, or any `package.json` above the analysed root up to the git repository root lists it; the same manifests enable
plugins.

**Packages tool configs name.** A package that a tool config names itself is a dependency of the package whose
directory holds the config: a `tsconfig` `extends`, `compilerOptions.types` or `compilerOptions.plugins` entry, an
Oxlint `jsPlugins` entry, an ESLint plugin, parser or shareable config, a Babel preset or plugin, a PostCSS plugin, a
Prisma `generator` `provider`, and what the other plugins read the same way, including a fixed name a plugin derives
from a config value (`importHelpers: true` names `tslib`), as knip does. A listed one is used; one no manifest lists
is reported by `unlisted-dependencies` at the config with the detail `ConfigReference`
("`tsconfig.json` references `@acme/tsconfig`, which is not listed in `package.json`"). Built-in names
(`prisma-client-js`, a `generator client` block), relative paths and the string `extends` of an ESLint flat config
(`js/recommended`) are no packages. A built-in ESLint config (`eslint:recommended`) is an optional reference to
`eslint`; knip credits it as a plain dependency, which it reports where no manifest lists `eslint`, but skif does not,
since a package that only enables ESLint may get it from the root. A package that a command in a config names (`node --require x`
in a hook), one a plugin assumes without reading a config, and an optional reference (Vite's `optimizeDeps.include`,
an `eslint-plugin-import` resolver) is only a use and never reported. A config that imports the package it names is
reported once, for the import.

A `tsconfig` compiler option (`types`, `jsxImportSource`, `plugins`, `importHelpers`) applies to each package that
reads the config, so a shared base config is satisfied when its owner or the package extending it lists the package;
an `ignore-dependencies` entry of the extending package silences it too. A `types` entry is satisfied by the package it
names or its `@types` package: `types: ["cypress"]` with `cypress` listed at the root needs nothing more, and
`@cloudflare/workers-types` or `@types/node` name themselves. `types: ["*"]` names no package: it keeps every `@types`
package visible, so a globals-only one such as `@types/chrome` counts as used. A config without `types` keeps them all
too before TypeScript 6, and none from TypeScript 6, which defaults `types` to `[]`: there an `@types` package is used
only when an import, a `types` entry or a `/// <reference types>` names it. A config's own `types` and `typeRoots`
replace the ones it extends, and a later `extends` entry overrides an earlier one. A solution config whose
`references` name other configs (`files: []` beside `tsconfig.app.json`) keeps every package when one of the configs
does. The version is that of the `typescript` installed in the nearest `node_modules` from the package up to the
workspace root, else the lowest version the package's `typescript` ranges admit (`^6`, `>=6 <8` and `6.1.0-beta` are
6; `<6` and `^5 || ^6` are below), a `catalog:` reference read from the workspace catalogs and a `peerDependencies`
range only when the package lists `typescript` nowhere else, else that of the root manifest; when none names one,
every `@types` package stays visible.

`ignore-dependencies` silences a package; a config below `node_modules`, that git ignores (generated, such as
`.nuxt/tsconfig.json`), in a fixture directory (unless `include-fixtures`) or matched by `ignore` is not judged.
Production mode judges no config, and so `--strict`, which implies it, judges none either.

`declare module 'pkg'` declares the package, so its imports need no dependency, and so does a pattern with a literal
start (`declare module 'pkg/*'`) for the imports it matches. A declared subpath (`declare module 'pkg/data.json'`)
declares that module only: the package's other imports still need it listed. An import that an alias leads into
another package (`react` to `preact/compat`) is covered by a declaration of any module of that package. A specifier
that names a workspace package is an import of that package also when a `tsconfig` mapping or a bundler alias resolves
it into the package's directory, to generated code there included; an alias into other code (`ui/*` to `./src/ui/*`
beside a workspace package `ui`) stays local.

A directory below a package with a `package.json` of its own that is not an analysed workspace member (one excluded
with `ignore-packages` included) is a separate project, often a root of its own in a recursive run (a `build` or
`scripts` folder with its own lockfile); a `package.json` holding only `type`, `sideEffects` or `imports` is a
marker for the files below it and makes no project. The files of a separate project are not
the analysed root's: when a script or an import of the root reaches one, that file is not reported in the root, and
its imports are neither unlisted there nor uses of the root's dependencies. The nested project judges the file against
its own manifest when it is analysed as a root of its own. In the other direction, a file of the
analysed root that a script of a `package.json` above it runs (up to the git repository root) is an entry, so
`node build/npm/postinstall.ts` in the outer project keeps `build/npm/postinstall.ts` used in the nested root at
`build` (except in production mode, where scripts give no entries).

In a multi-root run (`skif -r`) the files of a nested root that an enclosing root of the same run imports, runs from
a script or names in a tool configuration are entries of the nested root: `import { x } from "../build/lib/x"` in
the outer `src` keeps `build/lib/x.ts`, and what it imports, used in the root at `build`, and so does a workflow step
`node build/lib/report.ts` for `build/lib/report.ts`. Only the files the enclosing root's own code and configuration
reach directly become entries, so an unused export of a file they import is still reported. A nested root is therefore linted after the roots that enclose
it. A root linted on its own (`skif build`) cannot know what an outer root it was not given imports, so there such a
file is still reported unused; lint from the top with `-r`, or add it to `entry`.

A file a root's code reaches outside the root's own directory counts as used by the root of the run that holds it:
`require("../tools/detect.js")` in a nested root at `build` keeps the outer root's `tools/detect.js`, and every file it
imports in turn, out of `unused-files`, and so does an import of a file of a sibling root. The packages those files
import count as used by the manifest that lists them at or above the file, so a sibling's `lib.js` that requires
`lodash` keeps `lodash` out of that sibling's `unused-dependencies`. Those files are credited after every root is
linted, so their exports are not judged against that code; linted on its own, the owning root still reports them.

The other way round, a nested root that imports or runs a dependency it does not list itself, but a `package.json`
above it does, uses that dependency through the outer project's `node_modules`: Node.js resolves it from there. In a
multi-root run the root that owns that manifest (the innermost one that lists the dependency) then does not report it
in `unused-dependencies` or `unused-dev-dependencies`, so `gulp-rename` in the root `devDependencies` stays used when
only `build/lib/gulp.ts` of a nested root at `build` imports it. The outer root linted on its own cannot see the
nested root's code and still reports it.

A package with no source file at or below its directory, no entry and no script, such as a `remote/package.json` that
only lists what code elsewhere in the repository installs it for, has no code skif could check its dependencies
against, so they are not judged, as for a package whose entry files skif cannot determine. A pnpm install hook
(`.pnpmfile.cjs`, `.pnpmfile.mjs`) is no source file for this rule: it is an entry, so what it imports is used, but a
package whose only JavaScript it is stays unjudged.

A bare import of a builtin name (`import { EventEmitter } from "events"`) uses a listed npm package of that name, the
polyfill a bundler resolves it to for the browser; knip reports such a package unused. `node:events` names only the
builtin, and `events/` only the package.

The default `project` globs include `.vue`, `.svelte` and `.astro` files. Their `<script>` blocks (`<script setup>`,
`<script context="module">`, any `lang="ts"` or `lang="tsx"`) and the Astro frontmatter are analysed as modules, with
diagnostics located in the original file. The markup is scanned, not compiled: component tags (`<MyCard>`,
`<my-card>`, `<ui.Card>`), the expressions of `{{ }}`, `{ }`, `:prop`, `v-*`, `@event`, Svelte blocks (`{#if x}`) and
directives (`use:action`) count as uses of the imports they name, and a read such as `ns.member` counts as a use of
that member. `<style>` blocks and `src` attributes of `<script>` and `<style>` tags are imports. The expressions are
parsed as JavaScript, so a name an expression binds itself (`items.map((item) => item.id)`) is no use, and neither is a
template local: the alias of a Vue `v-for` and the props of `v-slot`, `#name` and `slot-scope`, and the names Svelte's
`{#each}`, `{#await}`, `{:then}`, `{:catch}`, `{#snippet}`, `{@const}` and `let:` bind, within the element or block
that binds them. A member that such a local of the same name as a namespace import reads (`item.title` under
`v-for="item in items"`) is no use of that namespace's export; a named import keeps its export used either way, as in
knip. An expression that does not
parse is read token by token, which can only make an import look more used. Nothing in a template is type-checked.
Imports of one script block count as used when another block reads them.

`.mdx` files are read without an MDX compiler: their top-level `import` and `export` statements (at the first column,
outside frontmatter and fenced code, as MDX delimits them) are analysed as JavaScript with JSX, and the prose is
scanned for the components and expressions it uses, as in a component template. Imports written in code samples,
inline code and frontmatter are not imports, and a component in a code sample or inline code (`` `<Card/>` ``) is not a
use. A reached `.mdx` file uses the `@mdx-js/*` and `remark-mdx` packages its
package lists. `.mdx` files are not in the default `project` globs: they are followed when an entry glob (Docusaurus
docs, Astro pages, Storybook stories) or an import reaches them, and reported as unused only when `project` names them.

The `templateUrl`, `styleUrl` and `styleUrls` of an Angular or Stencil `@Component({ … })` (the decorator imported
from `@angular/core` or `@stencil/core`) are imports of the component file, relative to it with or without `./`, so
the stylesheets are followed and the packages they import count as used. This includes Stencil's styles per mode
(`styleUrls: { ios: 'a.ios.css', md: ['a.md.css'] }`); its `assetsDirs` are directories copied as they are, not
modules, and are not followed. Vue auto-imports are followed through the
declaration files `unplugin-vue-components` and `unplugin-auto-import` generate (`components.d.ts`,
`auto-imports.d.ts`). A component `components.d.ts` registers from a file of the project is used where a template
uses its tag, as knip compiles it: each `.vue` file whose template names `AppButton` the way Vue resolves a tag
(`AppButton`, `app-button`, `appButton`, or `LazyAppButton` and `lazy-app-button`), in a static `is` attribute
(`<component is="AppButton">`, `:is="'AppButton'"`), and each file that calls `resolveComponent('AppButton')`, imports
the default export of the file `AppButton` is registered from. A registered component nothing uses so is reported by
`unused-files`, and so is what only it imports. Native elements (`<button>`) never name a component, and the imports
added for components are no `circular-imports` cycle. Registrations apply to every workspace of the run. A component
registered from a package stays an import of the declaration file. A package that may use its components in files
skif records no tags for keeps every component it registers used: one with a `.tsx` or `.jsx` project file, a
VitePress or VuePress site, or a bundler config that passes the plugin an `include` matching more than `.vue` files
(`/\.md$/`) or options skif cannot read. `auto-imports.d.ts` is an entry like every `.d.ts` file, so each composable
it registers counts as used, whether or not a file names it. A generated file that `.gitignore` excludes is not read,
and the components it registers then look unused.

Stylesheets that code imports are followed: `@import`, `@use`, `@forward` and the Tailwind at-rules of `.css`,
`.scss`, `.sass`, `.less` and `.pcss` files, and `@import` and `@require` of Stylus (`.styl`, `.stylus`, and
`<style lang="stylus">` blocks), where a bare name is looked up next to the file before it is taken as a package and a
glob (`@import "mixins/*"`) is skipped. A reached Stylus file uses the `stylus` package. `.tsrx` files (`@tsrx/core`)
are not TypeScript a parser accepts, so only their `import` statements and `import()` calls are read: the packages and
files they name are used, every imported binding counts as used as a whole, and their exports are not known, so a
re-export (`export { x } from './y'`) is not followed and `./y` is not reached through it. A reached `.tsrx` file uses
the `@tsrx/*` packages its package lists. Like `.mdx`, `.tsrx` files are not in the default `project`. `.marko`
files are read the same way, and so are the imports of their `<style>` blocks and concise `style { … }` blocks
(`style.less { … }` is Less, `style { … }` Sass); a tag import (`import Card from "<card>"`) names no module and is
left out. A reached `.marko` file uses the `marko` package, and `.marko` files are not in the default `project`
either.

Test files are entries when a test-runner plugin is enabled (Jest, Vitest, Mocha, Playwright, Cypress and the like),
with the patterns of that plugin; a project without a runner reports unused test files like any other, as knip does.
Jest's defaults include files named just `test.js` or `spec.ts`. Jest's `testRegex` (a string, a regular expression
or an array of them) selects test files too, besides the default test globs, which stay as knip keeps them; `testMatch`
adds to them as well. A `testRegex` is matched against `/` and the path relative to the package, `<rootDir>` standing
for the `rootDir` option (the config's directory by default) and anchoring the expression there when it leads; the
`i`, `m` and `s` flags of a regular expression literal apply. An expression the analysis cannot compile (a lookaround or
a backreference) leaves the package's files unjudged. `testPathIgnorePatterns` is not applied, as knip does not apply it
either. A Playwright `testMatch` regular expression becomes a glob
when it is made of literals, `.*`, character classes (`[jt]`), the `?` quantifier, anchors and groups
(`/.*\.e2e\.tsx?/` matches `**/*.e2e.ts{x,}*` below `testDir`); any other expression makes every script below
`testDir` an entry.
Add other test files to `entry`. Directories named `fixtures` or `__fixtures__` hold test data: their imports are not checked for unresolved or
unlisted packages, and their files are not reported by `unused-files` nor their exports by `unused-exports`,
`unused-types`, the namespace rules and `unused-enum-members`. **`include-fixtures = true`** reports those files and
exports like any other. A fixture file is still read when an entry reaches it, but one that nothing reaches is not, so a
dependency only an unreached fixture imports stays unused. Other directories of test data (`api-fixtures`,
`__testfixtures__`) and other test file names (`*_spec.*`) go on `ignore` and `entry`. In a package whose `exports` contain a wildcard (`"./*": "./src/*.ts"`) the
`*` matches across directories, as in Node.js, so every file it matches is an entry; the catch-all `"./*"` and the `main`, `bin` and `types` fields are not widened. In an enum or a namespace, a
member read in its own file (`E.A`, `E["A"]`, `const { A } = E`) counts as used; using the whole enum there
(`Object.values(E)`, `E[key]`, a spread, passing it as a value) or mentioning its type (`x: E`, `typeof E`) credits no
member, as in knip. Inside a namespace, a member read by its bare name (`findVisible()`, `token: ProgressToken`) counts
as used, unless a parameter or local of the same name shadows it; the declarations of a merged namespace share their
members. A file that another loads with `new URL("./x", import.meta.url)` is used as a whole. A module that a test mocks
(`vi.mock("x")`, `jest.mock("x")`, `jest.requireActual("x")` and the like, read from the syntax tree, so a call written
inside a string does not count) stays reachable, and a listed package it names is used, but mocking a package that no
`package.json` lists is not an unlisted import; a `{ virtual: true }` mock is ignored. A relative or aliased mock
whose module does not exist (`vi.mock("./gone")`, Vitest's `vi.mock(import("./gone"))`; a query such as `?react` is
dropped before resolving) is reported by `stale-mocks`, an error as such a call was under `unresolved-imports`, so that
it can be triaged or baselined apart; a package name that resolves to nothing is not reported. In an n8n node package
the files listed in `package.json` `n8n.nodes` and `n8n.credentials` are entries; a `dist/nodes/A.node.js` there maps to
`nodes/A.node.ts`, since such packages compile without a `rootDir`. The `vite` and `vitest` plugins honour Vite's
`root` (relative to the config file): `root: "src"` makes the scripts of `src/index.html` entries, and a `/`-rooted
script `src` or build input HTML file starts at `src`; a `root` that is not a static string leaves the
package's entries incomplete. The build input is read from `build.rolldownOptions.input` (Vite 8), else from
`build.rollupOptions.input`, as knip reads it.

A JavaScript or TypeScript config is evaluated statically. A value it imports from another file of the project, or from
a workspace package (through its `exports` or `main`, mapped back to the source file), is evaluated in that module too:
a base config merged with `mergeConfig`, spread into an object, or listed in an ESLint `defineConfig`. A value imported
from an installed package stays unknown, and an imported value that depends on itself through imports is unknown there.
A member of a known object is the value of its key: `{ ...base, plugins: [...base.plugins, "x"] }` keeps the plugins of
the imported `base`, which are judged against the package that owns the module naming them, while `"x"` belongs to the
importing config. An optional member (`base?.plugins`, `undefined` when `base` is `null` or `undefined`) and a computed
member whose key is a known string or number (`base["plugins"]`, `base[KEY]`, `LIST[0]`) read the same way. Only a fully known object answers for a key it does not have, which is `undefined` there, read
through a member or a destructuring; a key an unknown spread may set, a member of `Object.prototype` such as
`toString`, and any key of an object with a `__proto__` are unknown. A key merged from a spread with an unknown test
(`{ ...(ci ? { setupFiles: ["./a.ts"] } : {}) }`) may be absent, so `x.setupFiles ?? ["./default.ts"]` keeps both lists
and its `.length` is unknown. The same holds for every value that carries the read on: a constant or local holding it,
an object key it is put in, set on or merged into, a function argument, a function's return value, an array spreading
it, and a named export holding it in an imported module. A parameter or destructuring default applies to a key an object
does not have, but not to a literal `null`. A config function the tool calls (an exported function, the callback given to
`defineConfig`) has every parameter unknown, its default included, since the tool passes what the config does not say:
`(env = {}) => env.analyze ? a : b` keeps both branches. A config factory of a workspace package
(`createVitestConfig({ setupFiles: ["./setup.ts"] })`, also wrapped as `defineConfig(createBase(options))`) is called with the arguments given, so what it builds from its options is known. A
config that exports the result of a call that cannot be followed, such as a factory of an installed package, is
unknown and leaves the package's entries incomplete, but each string of the call's arguments that names an existing file
of the package as a path (`./setup.ts`, `test/setup.ts`), relative to the config file, is an entry, as are those of such
a call that the exported config function returns (`() => createConfig({ ... })`), that an exported `mergeConfig` is
given, or that sits below the top level of the exported config (`{ test: createTest({ setupFiles: ["./setup.ts"] }) }`). A bare name such as `chart.js` is a package even where a file of that name exists, and a file listed under an
exclusion key (`exclude`, `excludeFiles`, `watchExclude`, `coverage.exclude`, `ignores`, `ignorePatterns`,
`testPathIgnorePatterns`, `testIgnore`) is left out.
A conditional (`cond ? a : b`, `&&`, `||`, `??`) whose test is known takes its branch, so a key spread in only when
`pinCjs.length` is truthy is left out when `pinCjs` defaults to `[]`. A value with an unknown test is what both branches
share: a key only one branch sets is unknown and the other keys stay known. A spread with an unknown test
(`...(tmp && { cacheDir: tmp })`, `...(process.env.CI ? { test: { setupFiles: [...] } } : {})`) adds every key a branch
sets instead: a list gets the elements of every branch, so the files each branch names are entries, and any other value
the branches do not share is unknown. Only a branch that is not known itself, such as an imported base config, makes it
an unknown spread. The same holds for `if (test) return a;` before a function's last `return`: a known test takes its
branch, and with an unknown test the value is what both returns share, never the last one alone.
`.map`, `.flatMap` and `.filter` of a known array call their callback, an inline function or one the config declares,
with each element and its index, so `` ["light", "dark"].map((theme) => ({ test: { name: `browser-${theme}` } })) ``
is two known projects; an element that is not known (a spread of an unknown list) stays unknown, and a predicate whose
result is not known keeps the element. `Object.fromEntries` of a known list of `[key, value]` pairs is their object,
template literals and `+` write known strings, numbers and booleans, and `===` and `!==` compare known primitives. A
Vite or Vitest `root` that is one of several directories reads the HTML entries of each. A path function, a template
literal or `+` over a value that is one of several is one of the results of each, unknown when one is unknown or there
would be more than eight, so `path.join(dir, 'vitest.setup.ts')` with such a `dir` is one of two paths. A list of
files or patterns (setup files, test globs, bundler entries) whose value or element is one of several known strings
makes each an entry candidate; one that names no file is dropped without a hint.
A local assigned or changed in code that may or may not run (a branch with an unknown test, a loop, `cond && (x = 1)`),
and a top-level constant changed after its declaration (`if (process.env.A) config.plugins.push(…)`), is unknown or
partly unknown afterwards rather than keeping its earlier value; a branch with an unknown test that changes a local
leaves it what both branches have in common. Only the part a change reaches is affected: `config.module.rules.push(…)`
leaves `module.rules` partly unknown, `config.output.path = …` leaves `output.path` unknown, and the rest of `config`
stays known; `push` and `unshift` of a local list add their elements. A change below a key a known object neither
has nor inherits (`config.plugins.push(…)` without `plugins`) changes nothing, as reaching below `undefined` throws;
below a key an unknown spread may set or the object may inherit (`__proto__`, `constructor`), the object is partly
unknown. An object changed through another name for it
(`const a = cfg`, `{ test: t }`, `{ ...base }`, a function given `cfg`), by a function that writes what it captures, by
`delete` or inside an expression is partly unknown wherever it is read, in the part the change reaches; a write
through an object that is not a name or a member chain (`config.module.rules.find(…).loader = …`,
`(prod ? config.prod : config.dev).devtool = false`) reaches each part of a local that object may be. A call of a
function the config declares shares with what it is given only what the function may return of it: a fresh object
it builds shares nothing with its arguments, unless the function is used other than by calling it by name, calls
itself or reads `arguments`; a getter, method or callback in what it returns shares what that returns, and a
parameter shares its default (`b = a`). What a method returns (`config.plugins.find(…)`, `list.slice()`) may be a part of the
object it is called on. A `const` of a function that takes a local of that function,
or a static part of it (`const { coverage } = config.test`), is followed instead when it is the only such name for the
local, no other function shares either and the local is never assigned again: a change through it is applied to that part of the local, so
`coverage.enabled = true` in a branch with an unknown test leaves `enabled` one of both values and the rest of `config`
known. What else may hold that object (a list or object holding `config`, the options spread into it, another key of
`config` given the same object) is partly unknown where it is read after the alias is declared. A `resolve` call (`require.resolve`, `createRequire(...).resolve`) changes nothing, and neither do the functions
of `path`, `url`, `JSON` and `Math`, `fs.readFileSync` and the other reading functions of `fs`, `Object.keys` and
`console`, so a config holding `fs.readFileSync(CERT)` stays known; a `const` holding a string or a number shares no
object with what it is given to. These are known only where the name resolves to the module or global that declares
it, never a local of the same name. Any other call, a library's function or a `new` of a class other than a builtin one,
may change every object it is given, in any position and through a spread, and every local an object or array literal
it is given holds, at any depth (`kit.fill({ cfg: config })`, `foo([config])`, all of `options` for
`foo({ ...options })`), unless it is a `define…` helper of a library,
a merge that copies (`webpack-merge`, `deepmerge`, `defu`, the `mergeConfig` of Vite and Vitest), `createRequire`, or
`Object.assign`, `Object.defineProperties` or `Object.defineProperty` and `Reflect.defineProperty`, which change only
their first argument, the last two only the key they name when it is a string; these are no `define…` helpers. A `define…` helper and a merge that copies keep none of their
arguments in another, so a change of one argument leaves the others known. A list or string
method (`push`, `slice`, `concat`) changes at most its object only when that object is known to be a list or string,
and one that calls a function it is given with the list's elements (`forEach`, `map`, `reduce`) only when that
function is written in place or declared by the config and no `this` object follows it (`list.forEach(fn, thisArg)`);
an imported callback (`configs.forEach(withSentry)`) may change each element and that object. A local holding a
function the evaluator does not follow (`const addAlias = aliaser(config)`) may change what it was made from each time
it is called; one bound to an import or a `require` is taken to change none of the config's locals. A
change through an element of a list leaves every element open; a loop name, a callback parameter, a name a destructuring
assignment sets and a function assigned with `=` share with what they take, except the element a callback over a
`const` list of strings or numbers takes when no change reaches the list (its later parameters, such as the list
`forEach` passes, still share it); a value spread from an object literal (`...(ci ? { plugins: list } : {})`)
is shared at the key it is spread at only; a write through one key reaches another key of the same local that holds
the same object (`config.b = config.a`); a spread of a local (`{ ...options }`) copies its keys, so a change below
one of them (`options.coverage.enabled = true`) reaches the copy at that key only, and a new value of a key of either
leaves the other as it was; and a write in a class body leaves what it reaches unknown. A key a plugin reads files from that is unknown below
the top level, such as vitest's `setupFiles: isPostgres ? [...] : []` or a `test` object an unknown spread may replace,
leaves the plugin's entries incomplete instead of being read as empty.

Plugins read configs and sources statically and never run a tool, so some of knip's plugin behaviour has no
counterpart. These differences are deliberate:

- `react-router` reads `routes.ts` as text: the string literals that name a source file are route modules, and a
  `flatRoutes()` call makes the files of its routes directory (`rootDirectory`, `routes` by default) route modules.
  `ignoredRouteFiles` is not applied and routes a program computes are not known. `@react-router/node` and `isbot`
  count as used but not as production dependencies.
- `knex` finds `knex({ client: "pg" })` calls by scanning source text, so only a string literal `client` in an object
  literal argument counts.
- `gatsby` reads `setBabelPlugin({ name })` calls of `gatsby-node` files as text, whatever hook they sit in.
- `rsbuild` evaluates a config function once without parameters and does not call functions in `tools.rspack`.
- `rslib` and `preconstruct` entries are production entries; knip also marks their exports as used, skif follows `include-entry-exports`.
- `size-limit` credits every `@size-limit/*` package of the workspace, of any dependency kind; knip counts only
  `dependencies` and `devDependencies`. `size-limit.{json,js,...}` files are entries next to knip's
  `size-limit.config.*` and `.size-limit*`.
- `biome` resolves the `"//"` root reference to the `biome.json` of the farthest ancestor directory that has one.
- For `tsd`, `jasmine`, `ava`, `msw` and `oclif` the default entry patterns apply also when the config names others.
- Command lines are read from `package.json` scripts: `jasmine` and `tsd` positional arguments, `stryker run <file>`,
  `typedoc --plugin` and `--theme`. A flag that skif does not know takes the next word as its value, as `minimist`
  does, and `c8` and `dotenv` follow the command they wrap.
- `execa`, `zx`, `nano-spawn` and `pino` read the source files of the package as text before parsing those that
  mention the library. A command counts when it is literal: `execa("tsx", ["build.ts"])`, `` $`vite build` `` (the
  substitutions of a template are placeholders) or `spawn("eslint", ["."])`; a computed argument is left out, and a
  call with a literal argument that is not a plain word (`"a && b"`) is skipped. `execa` also reads the default export
  of execa 5 and earlier (`execa.sync`, `execa.command`, `execa.node`). `zx` reads `$` in files that start with
  `#!/usr/bin/env zx` and, unlike knip, also where `$` is imported from `zx`, in files that import `zx/globals` and
  under a shebang such as `#!/usr/bin/env -S npx zx`. In a file that switches zx to PowerShell (`usePwsh()`,
  `usePowerShell()` or `$.shell = 'pwsh'`), a cmdlet named `Verb-Noun` (`New-Item`) or a default PowerShell alias
  (`gci`, `ni`) is no binary.
- `bun` is enabled by `bun.lock`, `bun.lockb` or `bunfig.toml` in the package, a `bun test` script, or `@types/bun`
  or `bun-types` in the package or a package above it. Its test entries are the files `bun test` finds:
  `*.test.*`, `*_test.*`, `*.spec.*` and `*_spec.*` with any of the `js`, `jsx`, `ts`, `tsx`, `mjs`, `cjs`, `mts` and
  `cts` extensions; with `[test] root` in `bunfig.toml` only those below that directory (relative to the config), and
  without the files and directories a glob of `pathIgnorePatterns` (relative to the config too) matches. Entries set
  for the plugin in `[js.plugins]` replace these as before. `bunfig.toml` names the modules of `preload` and
  `[test] preload`, the package of `jsxImportSource`, the security scanner of `[install.security] scanner` and the
  ESLint plugins of `[lint] plugins`. In the source files, the commands of
  Bun Shell (`` $`…` `` imported from `bun`, or `` Bun.$`…` ``) and of `Bun.spawn` and `Bun.spawnSync` (a list of
  words, a computed one left out, or `{ cmd }`) are read like those of `execa`, and the `entrypoints` of `Bun.build`
  (or `build` imported from `bun`) are production entries relative to the package, the directory a script runs Bun
  in; one computed from the file's own location (`path.join(import.meta.dir, "worker.ts")`) is relative to the file.
  A command run in another directory, by `` $`…`.cwd(dir) `` or the `cwd` option of `Bun.spawn`, is judged as
  one run in another package, as `bun --cwd` is. Only the package's own sources are read: a workspace root does not
  read the files below a member's `package.json`. A package whose sources, or the sources of the packages below it,
  use the `Bun` global uses the `@types/bun` or `bun-types` it lists.
- `next-mdx` and `starlight` read the options of the `@next/mdx` and `@astrojs/starlight` calls in the config source;
  a plugin or component passed as an imported binding is not a string and is already an import.
- `unplugin-auto-import` and `unplugin-vue-components` make the declaration files they generate (`auto-imports.d.ts`,
  `components.d.ts`) entries. A local component `components.d.ts` registers is used only where a template uses its
  tag, as in knip, unless the package may use it in files skif records no tags for (see above); every composable `auto-imports.d.ts` registers is used, while knip credits one only in
  the `.vue` and `.ts` files that name it.
- `vue` reads `configureWebpack` as a webpack config. A function one is called statically with knip's base config
  (`mode`, empty `entry`, `resolve`, `plugins` and `module.rules`): the object it returns, or the base config as it
  leaves it (`config.entry = { … }`), is read; what it reads from its argument's members is not known, and an
  `entry` it sets to an unknown value marks the entries incomplete. It credits
  `@vue/cli-plugin-eslint` when a script runs `vue-cli-service lint`.
- `serverless-framework` reads `${file(./x.yml)}` and `${file(./x.yml):a.b}` variables. In a `handler`, a
  `${self:a.b}` variable is the string at `a.b` of the config, else its quoted fallback (`${self:custom.dir, 'src'}`),
  and any other variable (`${opt:stage}`, `${env:DIR}`, also `${opt:stage, 'dev'}`, whose fallback is only one of the
  values it takes), whose value is known only when the CLI runs, is a wildcard: `**`
  when it fills a path segment, as it may stand for several, and `*` within one. A wildcard is a trade-off: it can
  still miss files (a variable within a segment that stands for a path) and makes a wider entry, which can keep an
  unused file from being reported. A handler that is a glob is an entry glob, unless it names any file
  (`${opt:file}.main`).
- `github-action` leaves out the `dist/` and `build/` files an `action.yml` runs, as build output; knip also removes
  them from the project files.
- `azure-pipelines` (the `script` and `bash` steps of `azure-pipelines.yml`, `.azure-pipelines/**` and the templates
  they include) and `sapper` (its fixed client, server, service worker and routes) have no knip counterpart. `glob`
  is no plugin: the command of `glob -c "<command>" <patterns>` is read where the script parser meets it.
- `sst`, `quasar`, `stencil` and `orval` read their options wherever the config writes them (a `handler` inside
  `run()`, Stencil's `export const config`), as knip does. `sst` also reads the handlers of the modules
  `sst.config.ts` imports by relative path (`await import("./infra/api")`, `./infra/api.js` for `infra/api.ts`), so
  the SST 2 stacks of `app.stack(…)` too, and cuts the export off a `.route()` handler. It also reads the handler
  shorthand of SST 2 constructs: the string values of `routes`, `subscribers`, `notifications` and `targets`, and a
  `function`, `job` or `consumer` string. `quasar` takes the first `sourceFiles`,
  `boot` and `css` written anywhere.
- `qwik` and `stencil` need no compiler for `.mdx` or Sass files: skif reads every reached `.mdx` file and Sass
  stylesheet itself, so Qwik City's `.mdx` routes and the Sass of `stencil`'s component style URLs, which are imports
  of the component (see above), are read.
- `eleventy` reads `addPassthroughCopy("img")` and `addPassthroughCopy({ "src/js": "js" })` calls: a directory makes
  its JavaScript and TypeScript files production entries, a file or glob is one, and a path into `node_modules` names
  a package. A path computed from a local of the config function is not known.
- `rstest` applies `exclude` (a list or `{ patterns }`) and negated `include` patterns as `!` entries below the
  project's root, so its default test and mock globs do not bring an excluded file back. A `!` entry removes files from
  all the package's entries, so a file one project excludes is no entry of another project with the same root either;
  knip lists each project's files instead. Rstest's default exclusions (`node_modules`, `dist`, tool directories) are
  not added. `rs.mock("x")`, `rs.doMock()`, `rs.importActual()` and
  the other module calls of `rs` and `rstest` are mock imports, like `vi.mock()`.
- `react-email` credits `@react-email/ui` for a preview command from React Email 6 and
  `@react-email/preview-server` before, by the installed version (`node_modules/react-email/package.json` in the
  package or an ancestor up to the workspace root), else by the first number of the declared range; both when neither is known. `payload`
  keeps migrations and `payload-types.ts` from being reported through `ignore`.
- `mise` reads file tasks under the directories of `task_config.includes` or, when no config sets `includes`, under
  `mise-tasks/`, `.mise-tasks/`, `mise/tasks/`, `.mise/tasks/` and `.config/mise/tasks/`. A JavaScript or TypeScript
  file is an entry, and the command of its shebang (`#!/usr/bin/env -S npx tsx`) a script; a shell script (a shebang
  of `sh`, `bash`, `zsh`, `dash` or `ksh`, or without a shebang one of those extensions) is a script run in its
  `#MISE dir="…"` (also `# [MISE]`, `//MISE`) or the package. A task for another interpreter, or a file without a
  shebang whose extension is not a shell's (`README`), is not read. knip reads no file tasks.
- `taskfile` expands `{{.NAME}}` from the task's and the Taskfile's `vars` (a string only), `{{.ROOT_DIR}}` and
  `{{.TASKFILE_DIR}}`; any other template (`{{.CLI_ARGS}}`, an `sh:` variable, a function) is a word that is not
  known, so the rest of the command is still read, and an include holding one is skipped.
  `unplugin-vue-i18n` is no plugin: knip's has nothing to port.
- `marko` reads `.marko` files for their imports and style blocks (see above) but does not read the tag libraries
  of installed packages, so a package used only through its tags is not credited; it credits `marko` when a
  template exists. `unplugin-vue-markdown` is no plugin: skif compiles no Markdown.
- `varlock` reads the `@plugin` and `@import` decorators in the root comments of the `.env` files under
  `package.json#varlock.loadPath` and those a script passes with `--path`, but not `~/` paths, and does not skip
  git-ignored files; a `@plugin` version (`@varlock/1password-plugin@1.2.0`) is cut off. `railway` counts a service
  whose `source` is a call (`image("postgres")`) as local, and knows the local repository from
  `package.json#repository` only, not from the git remotes. A service `rootDirectory` is read from the repository
  root (`/apps/api` is `apps/api`); one with `..` drops the service's commands.
- `openclaw` and `typescript-content-mapper` are enabled by their `package.json` key. The files of OpenClaw
  `assetScripts` are entries, not production entries. `mdxlint` keeps a scoped plugin name as written.
- `solidjs-vite-plugin`, `filesystem-routing`, `vite-plugin-pages`, `vite-plugin-vue-layouts-next` and `flue` keep
  their conventional production entries when they read a config, as every plugin does; knip replaces them.
- An exported class registered as a custom element is used: `customElements.define("x-y", Class)` always counts
  (also through `window.customElements`, a variable holding the registry, or `this` in a static block), and so does
  the registering decorator of an enabled plugin's library on a top-level class: `lit`'s `@customElement`,
  `stencil`'s `@Component`, `catalyst`'s `@controller` and `fast`'s `@customElement`, or a `FASTElement` subclass
  that calls `Class.define()` or is passed to `FASTElement.define(Class, …)`. A decorator counts only when it is
  imported from that library. A variable holding the registry is resolved by scope; a local binding named
  `customElements` that does not hold the registry is not detected.
- `taskr` has no knip counterpart: `taskfile.js` and the local plugins of `package.json#taskr.requires` are entries,
  and `@taskr/*` and `taskr-*` dependencies count as used, as taskr loads them by name.
- `bazel` has no knip counterpart. It is enabled by a `BUILD.bazel` or `BUILD` file at the top of a package and reads
  the `BUILD` files below the package as Starlark text, never evaluated, in a Bazel repository whose `MODULE.bazel`,
  `REPO.bazel`, `WORKSPACE.bazel` or `WORKSPACE` names `aspect_rules_js` (the nearest one at or above the package,
  within the git repository). A label of the `node_modules` that `npm_link_all_packages` links for the package
  (`":node_modules/esbuild"`, `"//packages/app:node_modules/@types/node"`) and a load of a package's
  `package_json.bzl` (`"@npm//packages/app:esbuild/package_json.bzl"`) use that dependency; a label of another
  package's `node_modules` belongs to that package, so `"//:node_modules/typescript"` in a member's `BUILD` file uses
  the root's `typescript`. The `entry_point` and `data` of `js_binary`, `js_run_devserver` and `js_test` and the
  `srcs` and `data` of `js_library` and `ts_project` are entries (production entries except for `js_test`) when they
  name an existing file of the package, by path or as `":path"`; `glob()`, `select()` and variables name nothing, nor
  does a macro of a `.bzl` file. The `BUILD` files of a nested package give no entries, and those below the `bazel-*`
  links at the repository root are not read.
- A `tsconfig` with `outDir` maps build output back to source through its `rootDir`. Without one, skif takes the
  longest common directory of the `include` patterns (each up to its first wildcard) and the `files`, not counting
  declaration files; TypeScript computes it from the files it compiles. A config with neither keeps the `dist` to
  `src` convention. A file a script runs inside an `outDir` (`node build/src/cli.js`) is its source file, even when
  the build output is on disk, and a directory mocha is given (`mocha build/compiled/test`) stands for the code files
  directly in its source directory, or every one below it with `--recursive`. Only files with an `--extension` value
  (`js`, `cjs` and `mjs` by default) count, and in a source directory behind an `outDir` also the TypeScript sources
  that compile to them. An `include` entry without a wildcard is a file only when it ends in a code or `.json`
  extension (`packages/v1.2` is a directory).

## Layered configuration

A root takes every configuration file from its own directory up to the root of the git repository (the nearest
directory with a `.git` entry, a directory or a worktree file), farthest first, and merges them. Outside a repository
the search covers the root alone in a single-workspace run and the start directory in a recursive run. A file above
the repository is never read. A file with `root = true` ends the search at itself. `skif` inside a project and `skif
-r` from the top therefore give that project the same configuration. The guide
[Sharing configuration](../../guides/sharing-configuration/) shows complete examples.

### `root`, `extends` and `reset`

```toml
root = true
extends = ["../presets/node-cli.toml"]
reset = ["version-groups"]
```

- `root = true` stops the upward search at this file. It is only valid in a file found by discovery.
- `extends` lists files, relative to the declaring file or absolute. They apply before the declaring file, in
  order. A file reached twice applies once. A cycle, a missing file or more than 16 nested files is an error naming
  the file.
- `reset` discards what was inherited for the listed keys before this file applies. Allowed values:
  `version-groups`, `semver-groups`, `update-groups`, `custom-types`, `ignore`, `dependency-families`, `overrides`.

### Merge rules

| Value | Rule |
| --- | --- |
| Scalars (`fail-on-warnings`, `package-manager`, `mode`, ...) | The later file replaces |
| Tables (`[workspace]`, `[lint]`, `[policy]`, `[catalog]`, `[js]`, ...) | Merge key by key |
| Arrays of strings | The later file replaces |
| `extend-ignore-packages` (`[workspace]`), `extend-ignore`, `extend-ignore-dependencies`, `extend-ignore-binaries`, `extend-ignore-unresolved` (`[js]` and `[js.workspaces."<dir>"]`), `extend-exclude` (`[catalog]`) | Append to the inherited list, after the plain key of the same file |
| `[rules]` | Per rule: a level keeps the inherited options; a table of options replaces the options and keeps the level |
| `[js.plugins]` | Per plugin: `true` or `false` keeps the options; a table replaces them |
| `[js.compilers]` | Per extension: an entry replaces the inherited one |
| `[[ignore]]`, `[[overrides]]` | Append |
| `[[version-groups]]`, `[[semver-groups]]`, `[[update-groups]]` | The nearer file's entries come first, so with first match wins the project beats the org |
| `[[dependency-families]]`, `[[custom-types]]` | Replace the entry of the same `name`, append the others |

### `[[overrides]]`

```toml
[[overrides]]
packages = ["./legacy/**", "@acme/old-*"]   # directories start with ./, other entries are names
files = ["**/src/generated/**"]             # file globs, anchored at the declaring file
max-level = "warn"                          # cap the severity of matched diagnostics

[overrides.rules]
unused-exports = "off"

[[overrides.ignore]]
rules = ["unlisted-dependencies"]
dependencies = ["jquery"]

[overrides.js]                              # needs packages, no files
entry = ["src/server.ts"]
extend-ignore-dependencies = ["@acme/test-utils"]
```

At least one of `packages` and `files` is required; when both are set a diagnostic must match both. An override
changes how diagnostics in the selected packages or files are reported, and which JS inputs those packages get. It
never changes what a workspace-wide analysis computes, so a package leaves version policy through a root-level
version group with `policy = "ignored"`.

Package-scoped keys, the only ones an override or a package file may hold: `rules` (levels only), `max-level`,
`ignore`, and in `js`: `entry`, `project`, `ignore`, `ignore-dependencies`, `ignore-binaries`, the matching
`extend-` keys and `plugins`. Any other key, including rule options, `js.enabled` and `js.production`, is an error
that names the key, the file and the line. `[lint] max-level` caps a whole root and is allowed in a base file.
A plain `js` key replaces the inherited list, and `= []` clears it (`ignore-dependencies = []` lets a package report
what the workspace table ignores). A `dependency-types` entry may name a `[[custom-types]]` entry of an inherited
file; the names are resolved on the merged configuration.
A rule that is `off` in the base and on in an override runs; its diagnostics outside the override are dropped.

### Package files

A `skif.toml` in the directory of a workspace member applies to that package only, as if it were an override with
`packages = ["./"]`. It uses the top-level spelling (`[rules]`, `[js]`, `[[ignore]]`, `[lint] max-level`) and the
same package-scoped keys. Its `[[ignore]]` entries need no filter. `root`, `extends` and `[[overrides]]` are not
allowed in it.

### Paths

Patterns that select packages or files in an override, and `extends` paths, are relative to the directory of the
file that declares them. `$ROOT/` at the start of a pattern anchors it at the root being linted instead, which a
shared preset needs. A pattern that would leave its anchor (`../packages/*` in `config/shared.toml`) never matches, and a lint run warns about it on stderr, naming the file: write `$ROOT/packages/*` instead. Values are read in the scope they
configure: top-level `[js]` globs are relative to the root, `js` globs of an override or package file are relative
to each package. `ignore-packages`, `[[ignore]] packages`, group selectors and `[js.workspaces]` keys stay relative
to the root, with one exception: in a multi-root run with `--config <FILE>`, the `[js.workspaces]` keys and
`ignore-workspaces` globs of that file are relative to the directory the run starts at. `"."` is then the root in
that directory only, `"tools/sub"` the root in `tools/sub`, and `"tools/sub/packages/*"` the members of that root,
so one file can configure every root of the run by its directory. The keys then depend on where the run starts: from
the repository root the root in `tools/sub` is `"tools/sub"`, from `tools/` it is `"sub"`, so write the file for the
directory your recursive runs start at.

### Inspecting the result

`skif config --show` prints the effective configuration of each root as TOML with a `# from <file>:<line>` comment on
every value some file set (the last file to set it, plus the files that appended to a list), and lists the
`skif.toml` files below the root that were not applied, with the reason: only the root's own directory and the
directories of its workspace members are read. `--format json` adds the same as data: `origins` (every key with the
assignments that built it) and `not-applied` (path and reason). `skif config --explain <key> [--package <name>]` prints every file that
touched a key and the final value. `--config <FILE>` lints with that file (and what it extends) only, and
`--no-config` reads no file.

## Selectors

Every key that names packages or dependencies is a list of names and globs. `!` negates, and an invalid pattern is
a configuration error naming the key.

## Full example

```toml
#:schema https://raw.githubusercontent.com/Goldziher/skif/main/schema/skif.schema.json

[workspace]
ignore-packages = ["examples/*"]

[lint]
fail-on-warnings = true

[rules]
unsorted-dependencies = "warn"
empty-dependencies = "off"

[[ignore]]
rules = ["types-in-dependencies"]
packages = ["legacy-app"]

[catalog]
mode = "prefer"

[js]
enabled = true
```
